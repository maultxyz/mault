# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
pnpm install
pnpm dev                                      # turbo dev: Vite :5173 + Hono :3001, in parallel
pnpm --filter @magic-vault/server dev          # server only
pnpm --filter @magic-vault/web dev             # web only

pnpm build                                    # turbo build (tsup for server, tsc -b + vite build for web)
pnpm --filter @magic-vault/web lint            # eslint — the only package with a lint script

pnpm --filter @magic-vault/server db:generate  # generate a migration from schema.ts changes
pnpm --filter @magic-vault/server db:migrate   # apply migrations
pnpm --filter @magic-vault/server db:push      # push schema directly, no migration file (fast local iteration only)
pnpm --filter @magic-vault/server db:studio    # open Drizzle Studio
```

There is no automated test suite in this repo. `packages/server`/`packages/shared` have no lint script either — rely on the `web` build (`tsc -b`) and editor TypeScript diagnostics as the type-check gate for the other two packages.

See `CONTRIBUTING.md` for the full database-migration workflow and `README.md` for environment/Neon setup.

## Architecture

pnpm workspace + Turborepo, three packages: `shared` (framework-agnostic types/constants/rule engine, no build step — resolved straight to `src/index.ts`), `server` (Hono 4 API + Drizzle ORM + Postgres, either Neon-hosted or self-hosted — see Auth & RLS below), `web` (React 19 SPA). A single root `.env` is read by both the server (`tsx --env-file ../../.env`) and Vite (configured to read up from `packages/web`). `docker-compose.yml` runs a fully self-hosted stack (`AUTH_PROVIDER=local` + `pgvector/pgvector` Postgres, no Neon account needed) — see README's self-hosting section.

### Auth & RLS

- Two identity providers, selected by `AUTH_PROVIDER` (`neon`, the default, or `local`) — see `auth/index.ts`, which picks between `auth/neon.ts` and `auth/local.ts`'s `AuthProvider` implementations (`lib/interfaces/auth.ts`). `middleware/auth.ts`'s `requireAuth`/`requireOrg`/`requireRole`/`requireOrgRole` are provider-agnostic and delegate to whichever is active; route code never branches on the provider directly.
  - **`neon`**: Neon Auth issues JWTs, verified via JWKS (`auth/neon.ts`). Org membership and user lookups are raw SQL against Neon's own `neon_auth.*` tables (a separate Postgres schema Neon provisions, not modeled in this repo's Drizzle schema).
  - **`local`**: fully self-hosted — [own-auth](https://own-auth.com) issues opaque session tokens against the app's own Postgres (its `own_auth_*` tables, created by `own-auth migrate`, live in the same `public` schema as the app's own tables). `auth/local.ts` calls the `OwnAuth` engine's methods directly rather than mounting its HTTP handler, since that handler is cookie-oriented and doesn't expose organisations at all — this app is bearer-token-only everywhere (see `routes/local-auth.ts`). A per-user platform role (used by `requireRole("admin")`) has no own-auth equivalent, so it lives in the app's own `platformUserRoles` table instead.
- Middleware chain on org-scoped routes: `requireAuth` (verifies the `Authorization: Bearer` token via the active provider, sets `userId`/`userRole`) → `requireOrg` (reads the `X-Org-Id` header, resolves membership via the active provider, sets `orgId`/`orgRole`, and rebuilds `jwtClaims` to include `org_id`) → `requireRole`/`requireOrgRole` for authorization gates.
- `routes/stream.ts` (the shared SSE connection, `?token=` + `?orgId=` since `EventSource` can't set headers) sits outside the middleware chain, so it rebuilds what `requireAuth`/`requireOrg` would: `verifyRequestToken()` (accepts impersonation tokens too) and claims that include `org_id`, without which every `orgRls` table reads as empty. The web side opens it with `getRequestAuth()`'s token and `useOrg().activeOrg`, the same identity as every API call.
- Two DB access paths: `db` (`db/index.ts`, plain pool, no RLS) and `authQuery(jwtClaims, tx => ...)` (wraps a transaction, sets `request.jwt.claims`, and — in `local` mode only — `SET LOCAL ROLE authenticated`, since Neon's connection-level `pg_session_jwt` extension does that mapping automatically in `neon` mode instead). Use `db` directly only for intentional RLS-bypass work (the sync job, Discord webhook lookups, provider-specific user/org bootstrap). New tables holding user/org data should follow the existing `.enableRLS()` + `crudPolicy({ role: authenticatedRole, ... })` pattern in `db/schema.ts` — both providers rely on the same `authenticated` Postgres role and `auth_is_org_member()` function existing (Neon provisions them; `local` mode's equivalent is `db/bootstrap-local.sql` / `scripts/migrate-local.ts`).
- The web client mirrors this split: `lib/constants/auth.ts`'s `AUTH_PROVIDER` (from `VITE_AUTH_PROVIDER`) selects between the Neon-specific client (`lib/auth/client.ts`, `@neondatabase/neon-js`'s `BetterAuthReactAdapter`) and local mode's own bearer-token client (`lib/auth/index.ts`, `lib/auth/local-session-store.ts`), dispatched via module-level ternaries (e.g. `features/companies/api/use-organization.tsx`) rather than runtime branching inside shared hooks. Local mode covers sign-up/sign-in/sign-out/session/org-switch, its own org invite UI (`features/companies/components/local-org-invites.tsx`), personal API keys (`features/account/components/api-keys-manager.tsx`), and an org audit log (`features/companies/components/local-audit-log.tsx`) — email verification, profile/password editing, and multi-session management remain Neon-only (gated behind `AUTH_PROVIDER` at the route/component level, e.g. `app/routes/app/account.tsx`, `app/routes/app/settings.tsx`).

### Multi-TCG card search & sync

- Each supported game is a pluggable adapter under `packages/server/src/lib/adapters/<game>/` (currently `scryfall`, `gundam`, `pokemon`, `lorcana`, `onepiece`, `fab`, `yugioh`, `riftbound`, `swu`): a `search.ts` exporting a `CardSearchAdapter` (`search`/`searchById` → `PlayingCard`) and a `sync.ts` exporting a `SyncSource` (`fetchCards`/`fetchOne` → `SyncSourceCard`, for the admin bulk image-vectorization job). A `SyncSourceCard` also carries the source API's own card object, untouched (`withRawData`, pre-serialized to keep the worker's memory down), which is stored in `cards.data` and turned into a `PlayingCard` on read by the adapter's `normalizeStored`. So a sync source must fetch complete card objects, not just id/name/image, and must store them in the API's own shape, never a normalized one.
- Sync sources must only return one entry per distinct artwork. Foil is a property of a scan (`isFoil`/`foilType`), not a separate printing, so a source that lists foils as their own entries (SWU-DB's `Foil`/`Hyperspace Foil` variants, `059F` next to `059`) drops them; their foil price still arrives via the TCGplayer `Foil` sub-type on the same product id. Both sync embedding paths (`sync-job/worker.ts`, `routes/admin/shared.ts`) run card art through `toPortraitCardImage()` (`lib/card-image.ts`) first, since the sorter always sees a card portrait while landscape-printed cards (SWU Leaders and Bases, Riftbound Battlefields) come from their APIs landscape.
- `card-search/resolve.ts` maps a `Game.key` to its `CardSearchAdapter` (`ADAPTERS_BY_GAME_KEY`); `lib/sync-job.ts` maps it to its `SyncSource` (`SYNC_SOURCES`). Adding a new TCG means adding both, then creating a `Game` row (via the in-app Games Manager, not a code seed) with that key.
- Every adapter normalizes into the same `PlayingCard` shape (`shared/interfaces/card.interface.ts`) regardless of the source API's own shape — that's the app's canonical card schema. `PlayingCard.id` is always per-printing/per-art granularity (not per card name), since that's what gets vectorized and matched against a scan.
- Each `Game` carries its own admin-configurable `fieldDefinitions: FieldMeta[]`, read generically via `getByPath()` to drive bin rules, card-grid sorting, and Discord notifications. Don't hardcode source-specific fields (e.g. Scryfall's `prices.usd`) in anything meant to work across games. Rules store only a field's key and look up its path/type/label at evaluation time, so editing those takes effect everywhere automatically; renaming a key doesn't, so the Games Manager form tracks each row's `originalField` and sends `fieldRenames` with `PUT /games/:guid`, which (`lib/field-renames.ts`, in the same transaction as the game update, across every org) rewrites `bins.rules`, `bin_sets.repack_slots` and `bin_sets.auto_assign_field` for that game's presets via `shared`'s `renameRuleFields`. Any new place that stores a field key must be added there too. The Games Manager can export games (one, or all) as versioned JSON (`features/games/lib/games-export.ts`, schema `schemas/games-export.schema.ts`) and import them: a game whose key already exists is overwritten through the normal `PUT /games/:guid` (after a confirmation), any other is created. The file carries no `originalField`, so an import never sends `fieldRenames`, and operators aren't exported but rebuilt from `DEFAULT_OPERATORS_BY_TYPE`.
- Rules can also match per-scan state that isn't part of the card: `shared`'s `withScanRuleFields` appends built-in `isFoil` (Foil / Non-foil), `matchPercent` (numeric, the scan's match confidence as 0-100, via `cardMatchPercent`; null when the card has no `distance`, which no percent comparison matches; a correction counts as 100), `marketValueUsd`/`marketValueEur` (the card's TCGplayer and Cardmarket price via `cardPriceFor`, foil price for a foil scan, null without a price) and, for games with `foilTypes`, `foilType` fields to a game's `fieldDefinitions` (a game field with the same key wins). Their paths live under `$scan`, which no source API object has, so `getCardValue` falls through from `raw` to the `$scan` object that `toRuleCard(card, { isFoil, foilType })` attaches. Every rule evaluation (bin routing, auto-assign, repack and copy-limit bin contents, sound rules, server-side notification rules) must run on a `toRuleCard` card with the rule field list (`useBinConfigs().ruleFieldDefinitions` on the web), and the `$scan` card must never be saved. Text comparisons in `evaluateCondition` (equals, contains, starts/ends with, in, and the set operators) trim and lowercase both sides (`normalizeText`), so casing and stray spaces in a rule's value never matter; numeric comparisons are untouched. On a scan, foil comes from the scanner's foil toggle (`forceFoilType`), so it's known before routing.
- Search results are wrapped in an in-memory TTL cache (`card-search/cache.ts`'s `withCache`).
- Scanning never depends on a game's upstream API being up: matching, OCR and by-id lookups all read the stored cards, and the upstream fallback (only for rows without stored data) is wrapped by `withErrorHandling` with a `CARD_API_TIMEOUT_MS` timeout. For the same reason, `GET /public/health` (status footer, System Health page) only checks the database, not the upstream card APIs; don't add them back or gate scanning on them.
- The sync job stores each card's raw API object in `cards.data`, so the card routes go through `card-search/stored-cards.ts` rather than calling adapters directly: text search is a case-insensitive match against stored cards only, on name, set code, collector number, or set code plus number (`MH3 123`, `MH3-123`, `#123`, Pokémon-style `45/198`, leading zeros ignored; `printing-query.ts`), with number matches sorted first. The number comes from `cards.collector_number`, which every write of `cards.data` (the sync insert, its stored-data refresh, single-card sync) fills from the adapter's own `normalizeStored(...).collectorNumber` (`storedCollectorNumber`), since each source keeps it somewhere different. A new write path must set it too; `backfill:collector-numbers` fills rows written before the column existed. Only a game/language with no stored card data at all (e.g. right after a deploy, before its first sync) falls back to the upstream API's search, and by-id lookups (the scan path) read the stored card, falling back to the upstream API only when the row has no stored data.
- Prices come from a daily TCGplayer pull, not the stored card data: `scripts/sync-prices.ts` (`lib/tcgplayer-price-sync.ts`, run by an external scheduler, e.g. a Coolify scheduled task running `node packages/server/dist/scripts/sync-prices.js`, or in the self-hosted compose stack by the `prices` service, a shell loop over the same script every `PRICE_SYNC_INTERVAL_HOURS` that retries sooner after a failed run, e.g. before a fresh database has finished migrating) upserts tcgcsv.com's per-group prices into `tcgplayer_prices`, and `card-search/tcgplayer-prices.ts` overlays the TCGplayer market price (as `price`/`priceFoil`, falling back to mid when a product has no market price) plus its market/low/mid/high (`priceRange`/`priceRangeFoil`, shown in the card details) onto every card read through `stored-cards.ts`, keyed on `PlayingCard.tcgplayerId`. After the pulls, the same script resolves every stored printing's prices once into `card_prices` (`lib/card-price-refresh.ts`, keyed on `(game_key, lang, card_id)` like `cards`, read-only to users), only writing rows whose prices changed. Scanned cards never get prices written back: every read keys on `card_prices` instead. On the JS side `applyCardPrices(adapter, { gameKey, lang }, cards)` overlays the stored row and only resolves live (`resolveLiveCardPrices`) for a card that has no row yet (a card synced since the last price run). SQL-side reads (collection stats, price sorting on a `price`/`priceFoil`/`priceEur`/`priceEurFoil` field path, export, storage lists and values, `session_init`, the Discord bot) go through `lib/card-price-sql.ts` (`scannedCardPriceSql`, `cardPriceValueSql`, `cardWithStoredPricesSql`), which looks the row up through the card's collection and game. Everywhere, a null stored price falls back to the price saved on the scanned card at scan time. A game opts in via its adapter's `tcgplayer` (tcgcsv category id + which sub-types feed `price`/`priceFoil`). Games whose source has no TCGplayer product id (One Piece, Gundam, Yu-Gi-Oh!) supply a `productMatch` instead, resolved against `tcgplayer_products` (tcgcsv's per-group product listings, refreshed weekly by the same job) by printed number plus a per-game filter; several matched products (Yu-Gi-Oh!'s per-artwork cards span many set printings) combine into one range (min low, median mid and market, max high) with `printings` set. tcgcsv blocks generic User-Agents and asks for ~100ms between requests and one pull per daily build, which the job follows: every run first checks `last-updated.txt` (and Cardmarket's `Last-Modified`) and only downloads what changed, so running it more often than daily is safe. The full `card_prices` refresh only runs when something was actually pulled (or with `--force`); otherwise it only prices cards that have no row yet, which is also how a fresh install backfills the table.
- Cardmarket (EUR) prices come from the same `sync-prices` job, after TCGplayer: `lib/cardmarket-price-sync.ts` pulls Cardmarket's public daily dumps (`downloads.s3.cardmarket.com/productCatalog/priceGuide/price_guide_<gameId>.json`, plus `productList/products_singles_<gameId>.json` for games that match by name) into `cardmarket_prices`/`cardmarket_products`, skipping a game whose guide's `Last-Modified` is older than its last pull. Cardmarket writes `0` for "no trend", so every price is stored as null unless positive. `card-search/cardmarket-prices.ts` overlays `priceEur`/`priceEurFoil` (the average sell price, `avg`, falling back to trend when a product has none) plus `cardmarketPrice`/`cardmarketPriceFoil` (low, trend, avg, 7-day and 30-day avg). A game opts in via its adapter's `cardmarket` (Cardmarket game id). MTG (Scryfall `cardmarket_id`), Pokémon (TCGdex `pricing.cardmarket.idProduct`) and German Lorcana (`externalLinks.cardmarketId`) carry the product id; every other game supplies `productNames`, matched against the catalog's normalized name (`cardmarketMatchName`: accents stripped, punctuation collapsed, so `Name - Subtitle` matches `Name, Subtitle`), first name with any hit wins. Cardmarket's catalog has no set names or collector numbers (One Piece and Gundam put the number in the name), so a name match spans every printing and combines into one price (min low, median trend and each average) with `printings` set. `card-search/card-prices.ts`'s `applyCardPrices` runs both overlays and is what every read path calls.
- Which price an org sees is `org_settings.price_source` (`tcgplayer` default, or `cardmarket`), set from Settings > Pricing. Never read `card.price`/`priceFoil` directly for display or totals: go through `shared`'s `cardPriceFor`/`formatPrice` (web: `usePriceSource()`, whose context `AppProviders` fills from org settings and the public `/watch` page fills from the monitor-link response), and server-side through `loadOrgPriceSource` (`lib/price-source.ts`). Cardmarket prices are never backfilled with TCGplayer ones, so currencies never mix in a total. The Moxfield/Manabox exports stay TCGplayer USD since their headers say USD.
- Scans saved before `PlayingCard.raw` existed have no source card object, but `card_prices` is keyed on `card_id`, so they get current prices like any other scan. Only a card with neither a `card_prices` row nor `raw` (nothing to resolve live from) keeps its scan-time price.

### Soft deletes

- Nothing is hard-deleted except scanned cards (`collection_cards`, plus unmatched scans' photos), the synced card database (`cards`), and everything when a whole org is deleted (`purgeOrgData`). Every other user-facing delete sets `is_deleted` on the row instead: `games`, `announcements` (deploy ones too), `bin_sets`, `bins`, `devices`, `bin_routes`, `bin_heights`, `module_configs`, `collections`, `storage_locations`, `sound_clips`, `sound_rules`, `notification_rules`. A soft delete leaves children alone (a deleted collection keeps its cards and photos, a deleted bin preset its bins, a deleted device its configs and audit history), so a restore brings everything back. Deleting an active collection or bin preset also clears `is_active`, so restoring one never leaves two active.
- Every read, count and plan-limit check on those tables must filter `is_deleted = false` (including relational `with:` blocks and raw SQL), and so must lookups that attach something new to a row (a game picked for a collection, a clip picked for a sound rule). Writes that fix up every row regardless (`applyFieldRenames`, `clearOrgDiscordReferences`, `purgeOrgData`) deliberately don't filter, so restored rows stay consistent. Uniqueness that users can collide with is a partial unique index on live rows (`games.key`, `devices (org_id, hardware_id)`, `storage_locations (org_id, name)`), and the per-device upserts (`bin_routes`, `bin_heights`, `module_configs`) set `isDeleted: false` on conflict, since a soft-deleted row still holds the unique key.
- Platform admins restore items from Admin > Deleted items (`/app/admin/deleted`, `DeletedItemsManager`), backed by `GET /admin/deleted` and `POST /admin/deleted/:type/:guid/restore` (`routes/admin/deleted-items-sources.ts`, one list and restore per `DELETED_ITEM_TYPES` entry in `shared`). A restore only flips `is_deleted` back, after refusing anything that would collide with a live row (same collection, preset or location name, same game key, a board that has a newer sorter record, a bin number that's been configured again). A new soft-deletable table needs the column, filtered reads, and an entry in both lists.

### Deploy announcements

- `.github/workflows/deploy.yml` posts an in-app banner for the length of a deploy through `POST /announcements/deploy` and clears it with `DELETE /announcements/deploy` (`routes/announcements/deploy.ts`). Both take the `X-Deploy-Key` header checked against `DEPLOY_API_KEY` (`requireDeployKey`, unset = both refuse), not a user token. These rows carry `announcements.is_deploy`, so a new deploy announcement replaces any leftover one and the DELETE only ever removes deploy rows, never an admin's. Each one also gets an `endsAt` (`durationMinutes`, default `DEPLOY_ANNOUNCEMENT_DEFAULT_MINUTES`) so it expires by itself if the workflow dies before clearing it. The Coolify webhooks return once a deploy is queued, so the workflow treats a deploy as finished when `GET /public/version` reports the new release, then clears the banner (in an `always()` step, so a failed deploy clears it too). Every one of these steps is `continue-on-error`: the banner must never block a deploy. The workflow needs the `MAULT_API_URL` (the server's public base URL) and `DEPLOY_API_KEY` secrets.
- A deploy also pauses scanning. Both deploy routes broadcast `DEPLOY_STATUS_EVENT` (`shared`) to every open `/stream` (`lib/deploy-notice.ts`, `{ guid, message }` or null), and a stream that connects mid-deploy gets the active one on connect. The web keeps it as `useDeployNotice()` (`lib/app-stream.tsx`). Each station's `ScannedCardsProvider` calls `useDeployScanPause`, which handles each deploy guid once: if that station is scanning (`scannerRunning`) and the org hasn't turned it off (`org_settings.pause_scanning_on_deploy`, Settings > Scanning, on by default), it calls `useAutoFeed`'s `pause()` and reports its `resume` to the tab-level `DeployPauseProvider` (`features/scanner/api/use-deploy-pause.tsx`), which shows one `DeployPauseDialog` for every paused station. The dialog can be dismissed (stay paused) or resume every paused station straight away; nothing waits for the deploy to finish. Because a guid is only handled once, the stream reconnecting to the new server mid-deploy never pauses a station again. The broadcast is in process memory, so it only reaches streams on the server process that received the deploy POST.

### Bulk sync job

- `lib/sync-job.ts` runs a single global in-memory job (one sync at a time), streamed to the admin UI over SSE (`routes/admin.ts`'s `/sync/stream`, via `hono/streaming`'s `streamSSE`). The JWT is passed as a `?token=` query param since `EventSource` can't set custom headers.
- Cards are fetched, vectorized (CollectorVision's Milo embedder, `lib/milo.ts`/`lib/vectorize.ts`) across `VECTORIZE_CONCURRENCY` parallel workers, and inserted in batches (`SYNC_INSERT_BATCH_SIZE`). Cards already vectorized (and so skipped) still get `cards.data` refreshed in batches first, so a plain non-forced sync backfills card data and keeps prices current without re-vectorizing. `processed`/`errors` counts only advance once a batch insert is confirmed — never when a card is merely queued into a pending batch — since several cards can share one batch's outcome.
- Job state lives in server process memory, not the DB, so it survives a page refresh but not a server restart; reconnecting SSE just flushes current state.
- The worker is a forked child process reporting over IPC. IPC sends are async, so it exits only once its final message has flushed (`exitAfterFlush` in `lib/sync-job/worker.ts`), and the parent watches `close`, not `exit`, since `exit` can fire before the last messages are read. Otherwise a finished sync reports "exited unexpectedly (code 0)".

### Scanning & hardware routing

- Card identification is a [CollectorVision](https://github.com/HanClinto/CollectorVision)-family pipeline: a corner detector (currently `HanClinto/ccgdetector-fastweb-single`, MIT — swapped in from the original AGPL Cornelius model since it shares the identical 384×384-in / corners+presence+sharpness-out contract) finds the card and perspective-dewarps it to a canonical 448×448 crop, and Milo (`HanClinto/milo`, AGPL-3.0, 128-dim, L2-normalised) embeds it. Both run as raw ONNX graphs (not through `@huggingface/transformers`) — client-side via `onnxruntime-web` (`features/scanner/lib/cornelius.ts`, `perspective-warp.ts`, `milo-client.ts`, `onnx-runtime.ts`), server-side via `onnxruntime-node` (`lib/milo.ts`) for the sync job and the server-side scan fallback, which only ever runs Milo — sync-source images are already clean single-card crops, and the server-side live-scan fallback intentionally skips corner detection/dewarp entirely (client-only capability), so match quality there depends on the static scan-region crop, not a real detection. Model weights are pinned by exact HF revision + SHA-256 and pulled at runtime rather than committed to the repo — server-side via `lib/models/model-registry.ts` (downloaded once, cached to disk, verified by SHA-256 before every use); client-side via `features/scanner/lib/model-fetch.ts` (downloaded via `fetch()`, cached in IndexedDB, same verify-by-hash pattern) — mirroring the old SigLIP Docker pre-download pattern's "pin and verify, don't trust a moving registry" approach without committing binaries to git. `cards.embedding` is `vector(128)`; there's no per-crop-region embedding (art/name/bottom) anymore — one embedding per card, matched via a plain top-K cosine search (`routes/card/shared.ts`). Both scan routes (`/cards/by-vector`, `/cards`) return the matched cards themselves: `attachMatchedCards` fills `SearchCardMatch.card` (priced, via `searchCardById`) for every match within `CLOSE_MATCH_DELTA` of the leader, so the scanner doesn't make a per-match `getCardById` round trip (it still falls back to one if `card` is missing). `/cards/by-vector` only needs the image for OCR, so the scanner skips encoding and uploading the JPEG when OCR is off. Swapping the embedding model is a breaking migration (see `drizzle/0037_little_marvel_apes.sql` for the pattern: truncate `cards`, alter the vector dimension, drop the per-game HNSW indexes, force-resync every game afterward via the admin sync panel's "Force full resync", which rebuilds `game-vector-index.ts`'s indexes automatically).
- The physical sorter's serial protocol is documented standalone in `firmware/PROTOCOL.md` — read that rather than re-deriving it from the web client.
- The firmware runs every command on the `loop()` task, one at a time: `handleCommand()` holds `commandInProgress`, and `waitMs()` keeps pumping Serial/BLE input during a command so new lines get an immediate `{"error":"busy"}` instead of running afterwards. On ESP32, BLE writes are only queued by the Bluedroid callback (`ble_esp32.ino`'s RX ring) and drained by `blePoll()`, never handled on the BLE task, so two commands can never drive servos concurrently. Any new blocking wait in the firmware must go through `waitMs()`. Because a `busy` reply answers a later command while an earlier one is still pending, `use-serial.tsx` hands it to the second-oldest waiter.
- Shareable monitor links: the monitor page's Share dialog (`features/collections/components/share-monitor-link-dialog.tsx`) mints a signed HS256 token (`lib/monitor-links.ts`, `MONITOR_LINK_SECRET`, unset = feature off) holding the collection guid, its org, an expiry (`MONITOR_LINK_EXPIRY_DAYS` in `shared`) and the collection's `monitor_link_version`. The public `/watch/:collectionGuid?t=` page (outside the auth guard and `AppProviders`) validates it via `GET /public/monitor-link`, then opens `/stream?share=`, which streams only that collection's session events: no org locks, no member names (`viewers_updated` is dropped, and the guest joins the session as "Guest"). Because a guest isn't an org member, its `session_init` is loaded through `db` (RLS bypass) scoped to the token's guid + org. "Revoke all links" bumps `monitor_link_version`, which fails every outstanding token's version check and closes their open streams (`closeMonitorLinkStreams`); streams also close at the token's expiry. Both pages render the same `SessionMonitorView`; the public one passes `showBinLocation={false}` since `BinLocationDiagram` needs the station-scoped bin providers.
- The monitor (`SessionMonitorView`, both `/app/monitor/:guid` and the public `/watch` page) loads cards exactly like the main grid: server-side pages and stats with the same search/sort/filter/grouping params (`features/scanner/api/monitor-cards.ts`; members hit `/collections/:guid/cards[/summary]` and share the grid's `collection-cards` query cache, link viewers hit `/public/monitor-link/cards[/summary]`, both backed by `routes/collections/cards-read.ts`). - A scan can be pinned to one set, like the foil toggle pins a foil type: the scanner controls' set picker (`ForcedSetPicker`, `ScannedCardsProvider`'s `forceSetCode`, reset when the station switches collection) lists the game's sets from `GET /cards/sets` (`lib/card-search/card-sets.ts`: one stored card per `set_code` normalized for its `setName`, cached per game and language). `use-card-scanner.ts` sends it as `preferredSetCode` with every match request (`MatchScope`). - A scanned card is routed as soon as it's matched, in parallel with saving it (`addCard`/`addUnmatchedCard` in `use-scanned-cards.tsx`), not after the save returns, since `POST /collections/:guid/cards` sat on the critical path between match and sort. Bin capacity is checked locally first (`useComputedBinFillLevels`, the bin meter's data, plus `pendingBinCardsRef` for cards routed but not yet reflected in the refetched counts, released only after `invalidateCollectionCards` resolves); the server's `findFullBin` (one query) and plan checks stay as a backstop. Capacity always comes from the device's calibrated bin height divided by the game's card thickness (`computeBinCapacity`, shared by the meter and `findFullBin`): a bin with no saved height counts as the Small preset (`DEFAULT_BIN_HEIGHT`, which is what the calibration picker shows for it) and a game with no thickness uses `DEFAULT_CARD_THICKNESS_MM`. - Unmatched scans record why they failed: `unmatched_cards.diagnostics` (jsonb, `UnmatchedScanDiagnostics`) plus the scan's own `embedding` (`vector(128)`, never sent back to clients). `findCardMatches` returns `diagnostics` (reason `too_far`/`ambiguous`/`empty_index`, nearest candidates, thresholds in force) only when it finds nothing, and `/cards` adds its server-side embedding there, since the client has none on that path. The scanner adds `no_consensus` (attempts matched but disagreed, so `matchesNeeded` wasn't reached) and `lookup_failed` (matched ids whose card couldn't be loaded), plus corner-detection and per-attempt details (`toScanOutcome` in `use-card-scanner.ts`). `session_init` leaves diagnostics out to stay small; the unmatched list route and `unmatched_added` event carry them. Matched scans store theirs too, in `collection_cards.diagnostics` (`MatchedScanDiagnostics`: matched by embedding or OCR, candidates, attempts, detection, OCR readout), sent with `POST /collections/:guid/cards` but never returned by card lists or stream events: the card detail panel's "Technical details" toggle loads it on demand from `GET /collections/:guid/cards/:scanId/diagnostics`, like the scan image. Manual adds and scans from before it existed have none. - A correction (`correctCard`) or an identified unmatched scan keeps the card's saved `binNumber` as the bin it physically sits in, works out where it belongs now (`resolveCorrectedBin`: the usual routing plus auto-assign, except chaos mode keeps a card already in a non-catch-all bin) and opens `BinCorrectionDialog` from `ScannedCardsProvider` showing both. Orgs that leave corrected cards where they were sorted turn that prompt off (`org_settings.correction_bin_prompt`, Settings > Scanning, on by default): the dialog is skipped and the card keeps its saved bin. Only its "I moved it" button changes the saved bin (`PUT /collections/:guid/cards/:scanId` with just `binNumber`, which doesn't count as a correction), so bin fill counts follow the physical card. Enter or Space (`BIN_CORRECTION_CONFIRM_KEYS`, handled on the dialog itself since app hotkeys are off while a dialog is open, and ignoring key repeat so a held Enter from picking the correction can't confirm it) runs the primary action, and Esc closes it as leave-where-it-is. With `org_settings.correction_auto_close_seconds` set (Settings > Scanning, one of `CORRECTION_AUTO_CLOSE_SECONDS_OPTIONS`, null = off), `CorrectionAutoCloseTimer` fills a ring around a check over that time, turns it green, and shortly after accepts the move (or just closes when nothing needs moving).
- OCR (a per-org opt-in, `org_settings.ocr_enabled`, toggled from Settings by `OcrToggle`, which shows `OcrBetaDialog` before turning it on; it only takes effect for games with `OCR_REGIONS_BY_GAME_KEY` entries in `shared`) never runs on a confident match: `needsTextSearch` in `use-card-scanner.ts` only calls `POST /cards/by-text` when the embedding search found nothing (`too_far`/`ambiguous`) or several matches within `CLOSE_MATCH_DELTA`. It sends its own 630×880 dewarp from the same detected corners (the 448×448 embedding crop is square, which squashes text), rotated to the winning orientation, then tries the other orientation's crop and embedding if nothing matched. The server reads each region's `field` (`name`, `setLine`, `number`) with tesseract, as a single line unless the region is `multiline` (Gundam's name bar moves with the text box length, and SWU/Lorcana print a subtitle that's part of the stored `Name - Subtitle`). All OCR goes through one queued worker, since the line/block mode is a worker-global parameter. For a multiline name, the joined text and each line are tried as separate name queries and the best-scoring one wins. It fuzzy-matches the name against `cards.name` (`pg_trgm`, `cards_name_trgm_idx`, `OCR_NAME_MIN_SIMILARITY`), keeps only the printings of the best-matching name, and ranks them by set-code match in the set line, then collector-number match (digits from the `number` region, or from the set line for games without one, where One Piece, Gundam, Yu-Gi-Oh! and FaB print set code and number together; a printed total like `/198` is ignored and leading zeros don't matter), then embedding distance, with no distance cutoff. When the embedding search itself found nothing and OCR supplied the card, the scan is saved with `collection_cards.needs_review` set, which shows the same review badge as multiple close matches and counts toward the "needs attention" filter. Either kind of flagged card is resolved by correcting it or by the detail panel's "Mark as correct" (`PUT /collections/:guid/cards/:scanId` with `confirmed: true`); both set `is_corrected`, which here means "reviewed": the badge turns green and the card leaves the "needs attention" filter. Only a real correction calls `markScanCorrected`, so confirming doesn't count as a wrong scan in `scan_stats`; OCR only breaking a tie between close embedding matches doesn't set it. Only the corner-detected path OCRs; the static-crop server fallback (`/cards`) doesn't. Regions are normalized to the portrait card, so they overlay the saved 448×448 debug image too. That square image is the dewarped card squashed to a square, so every place that shows a captured scan (detail panel, image viewer, unmatched list and popover, identify dialog, scanner debug preview, mobile drawer) displays it in an `aspect-[2.5/3.5]` frame with `object-fill`, which stretches it back to the card's real proportions.
- Scan photos go to Neon Object Storage (S3-compatible, private bucket) when `SCAN_IMAGE_BUCKET` and the `AWS_*` credentials are set, and stay inline in Postgres (`captured_image_data_url`) otherwise, e.g. the self-hosted docker stack. `lib/scan-images.ts` owns it: `storeScanImage` uploads before the save's transaction (so it isn't held open during network I/O, and falls back to the data URL if the upload fails); the add routes delete the object again if the save is rejected. Rows store `captured_image_key` under `orgs/{orgId}/collections/{collectionGuid}/{cards|unmatched}/{scanId}.jpg`, so card and org deletes clean up by exact key or prefix after their transaction commits (a collection delete is soft, so its photos stay). Unmatched deletes stay soft (`isDeleted`), but they null the row's image key and data URL and delete the object too, since nothing can show a deleted unmatched card's photo. Every read goes through `resolveScanImageUrl`, which returns a 1-hour presigned URL for a key or the legacy data URL, so both formats work side by side; the detail panel's image query refetches within that window (`SCAN_IMAGE_URL_STALE_MS`). `scripts/migrate-scan-images.ts` (`migrate:scan-images`) backfills existing rows.
- Sound rules (`/app/sounds`, `features/sounds`, `routes/sounds`): per org and game, an ordered list of `BinRuleGroup`s (built with the bins `RuleGroupEditor`, so for the active collection's game), each pointing at an uploaded clip (`sound_clips`, max 1 MB and 50 per org, MP3/WAV/OGG/WebM/M4A/AAC). - `lib/scan-lock.ts` prevents two concurrent scan sessions against the same collection. Every saved scan renews its collection's lock for `SCAN_LOCK_TTL_MS`, so the live locks double as the admin page's "Active scanning" panel (`GET /admin/active-scanning`): people scanning (distinct lock users), collections being scanned, organizations, connected sorters (`countConnectedSorters` over the device leases) and scans saved in that window (`scan_stats.created_at`). Locks and leases live in process memory, so these counts cover one server process and reset on restart.

The match percent is the scan-time value and doesn't change when the card is later corrected. `vectorized_on` (`web` for the in-browser Milo path, `server` for the `/cards` image fallback) arrives with the save as `ScannedCard.vectorizedOn`/`UnmatchedCard.vectorizedOn`, set by `use-card-scanner.ts` and passed through `addCard`/`addUnmatchedCard`. - Daily scan usage (the free plan's `FREE_PLAN_DAILY_SCAN_LIMIT`, and `cardsScannedToday` on the billing page) is a per-org, per-UTC-day counter in `org_daily_scan_usage` (`lib/scan-usage.ts`), never a count of `collection_cards`, since deleting cards or backdating the client-supplied `scannedAt` would otherwise refund quota. Users can only read it (RLS `modify: false`); `cards-add.ts` increments it through `db` with one conditional upsert, right before the insert and after every other check, so it's atomic under concurrent scans and a retried `scanId` isn't counted twice. `org_billing` is read-only to users the same way (its `plan` gates limits), so it's written only through `db`: `routes/billing/checkout.ts` (Stripe customer id), the Stripe webhook, and `purgeOrgBilling` (`lib/org-purge.ts`), which org deletion calls after its `authQuery` purge commits.

In-memory like the scan lock, so a restart just makes clients re-acquire.

- One browser tab can drive several sorters at once as "stations" (`features/scanner/api/use-stations.tsx`). - Auto-feed can pipeline scanning with routing, behind a per-device experimental flag (`devices.pipelined_feed`, off by default, toggled from the Experimental panel on the calibration Modules & Routing page, `features/calibration/components/experimental-features-panel.tsx`): while auto-feed and the flag are both on, `routeCardToBin` sends `route` with `feedNext`, so the firmware feeds the next card as soon as the current one has left module 1 and reports it with an unsolicited `{"event":"fed"}` line (`firmware/PROTOCOL.md`). `use-auto-feed.ts` turns that event into the card-arrived hook, so the next scan runs while the previous card is still travelling; a routed response carrying `fedNext` skips the separate `feeder` command, and one without it (pre-2.1.0 firmware) falls back to `triggerAutoFeed()`. `use-serial.tsx` never hands `event` lines or `jam` errors to a waiting command, and `sendRoute` queues routes rather than rejecting while one is in flight. A route queued behind one that failed resolves `{ skipped: true }` without being sent, since the sorter may still hold the failed card.
- Nothing turns auto-feed off automatically: it's purely the user's setting. Errors, jams, an empty feeder, a hidden tab and the Pause button all call `useAutoFeed`'s `pause()`, which halts feeding (`isAutoFeedEnabled()` reads false while halted, so routes stop sending `feedNext` and `triggerAutoFeed` isn't called) without touching the setting. A card that still arrives while halted (a pipelined `fed` event already in flight) is held in `heldCardArrivalRef` rather than resuming the scanner. Resume, jam "Mark cleared" and the bin-limit dialog all go through `handleResumeScanning`, which clears the halt and either scans the held card or feeds a new one when auto-feed is on.
- Feeder rollback (firmware 2.4.0+): friction from the feed roller can drag the next card in the hopper forward a little on every feed until two go in together. `feeder_configs.reverse_duration` (ms, 0 = off, the default) and `reverse_speed` (a raw pulse on the far side of the motor's stop point from `speed`) make `runFeeder()` spin the roller backward for that long right after a card reaches module 1 (`rollBackFeeder()`, called once the motor stops), only while the hopper still has cards. They're part of `FeederCalibration`, so they ride along with every `setFeederConfig` sync; older firmware ignores them, so the calibration panel locks the rollback controls below 2.4.0 (the `feederRollback` firmware feature). Too long a rollback can drag the just-fed card back out of module 1, so it should stay short.
- Paddle open delay (firmware 2.6.0+): `ServoCalibration.paddleOpenDelay` (`module_configs.paddle_open_delay`, default 300 ms, the old fixed `DELAY_PADDLE`) is how long a module's side paddle gets to lower before its pusher fires, in `route`, `pushTest` and the push safeguard. Its slider on the calibration grid is gated behind the `paddleOpenDelay` firmware feature. Adding it grew the firmware's `ModuleConfig`, so the stored-calibration EEPROM layout went to 2 and `loadStoredConfigV1()` still reads layout-1 data (with the default delay); a later `ModuleConfig` change needs the same kind of migration. 2.5.0 boards don't report the field from `getStoredConfig`, so `parseStoredModule` fills `STORED_SERVO_CALIBRATION_OPTIONAL_FIELDS` with defaults instead of treating the stored copy as missing.
- Stored calibration (firmware 2.5.0+): the board keeps its channel offset, module and feeder calibration in EEPROM (`storeConfig`, data flash on the R4, NVS on ESP32) and applies it on boot. `setConfig`/`setFeederConfig`/`setChannelOffset` never persist by themselves, so calibration-page drafts sent for preview never reach flash; only `DeviceCalibrationSyncProvider`'s `applyToDevice` (module and feeder saves, history reverts) and the connect sync send `storeConfig`. That provider owns the single pre-test hook that syncs calibration: it reads the stored copy back with `getStoredConfig` (one section per line, since BLE replies are capped at 255 bytes), skips pushing anything when it matches the app and isn't `dirty`, and when it differs opens `CalibrationConflictDialog` so the user picks the app's values (pushed and stored) or the sorter's (saved to the app through the normal module/feeder PUTs, so they show in the calibration history). The channel offset is never part of the choice: the app's layout always wins. Firmware without the command answers `unknown command`, which falls back to the old push-everything sync without storing.
- Features that need a minimum firmware are listed in `shared`'s `FIRMWARE_FEATURE_MIN_VERSIONS` (keyed by `FirmwareFeature`; check with `isFirmwareFeatureSupported`). In the web app, wrap the controls in `FirmwareFeatureGate` (`components/firmware-feature-gate.tsx`), which shows a "requires firmware X" note and makes its children `inert`, or read `useFirmwareFeature(feature).isLocked` directly. A feature is only locked while a sorter is connected and its firmware is older than the minimum, or reports no version at all. With no sorter connected the version is unknown, so nothing is locked. The lock only covers the UI. Firmware ignores fields and flags it doesn't know, so runtime paths that send them (e.g. `feedNext`) still need their own fallback for older boards. A new firmware-dependent feature gets an entry in the map instead of its own `*_MIN_FIRMWARE` constant.
- Push safeguard (firmware 2.3.0+): a pusher never leaves neutral unless that module's side paddle was last commanded to `paddleOpen` at least that module's `paddleOpenDelay` ago, card on the platform or not. It's enforced inside `setServoPosition()` itself, which calls `lowerPaddleForPush()` (lowers the paddle if it isn't known to be down, then waits out the rest of `paddleOpenDelay`) before any off-neutral pusher write, so every path, including calibration previews and raw `channel` writes, is covered without refusing the command. There's no paddle position sensor: `setServoPosition()` tracks each paddle's commanded state (`paddleOpenedAt`), and `releaseIdleServos()` clears it. Pusher moves must always go through `setServoPosition()`, never a direct `pwm.setPWM`. 2.2.x firmware instead refused pusher moves with `{"error":"push_blocked"}` (only while IR read a card), which `use-serial.tsx` still turns into a toast.
- Jams surface through one toast (`features/scanner/api/use-jam-toast.tsx`, created once in `ScannedCardsProvider` and exposed as `showJamToast`) from two paths: the unsolicited `{"error":"jam"}` line (`card-scanner.tsx`, ignored entirely unless the scanner status is in `SESSION_TIMER_RUNNING_STATUSES`; auto-feed defaults to on, so it's a preference, not a sign a session is running. It only pauses once `useVerifyJam` confirms it: a module 1 jam is always dropped, since module 1 is the scan position and a card waits there for as long as matching takes, and any other module must read a card on every one of `JAM_VERIFY_SAMPLES` `readIR`s. `useSerial().readIR` runs through the route queue, so it never collides with a route in flight and reads the sensors only after that route finishes) and a `route` that still times out after the firmware's own paddle-flap retry (`route-card-to-bin.ts` matches `ROUTE_TIMEOUT_MODULE_PATTERN` on the error string, since that response carries no `module` field). The toast is keyed per module, so a jam the firmware keeps re-reporting replaces its toast instead of stacking. Both buttons render in one row inside the toast body (`jam-toast-body.tsx`), not as Sonner's `action`/`cancel`, so neither closes the toast by itself. "Drop card" (`clearDevice`) only updates the toast's text. "Mark cleared" re-reads IR, refuses while the module still reads a card, and otherwise calls `useAutoFeed`'s `resume()`, which runs the scanner's registered resume hook (`card-scanner.tsx`'s `handleResumeScanning`: resume, then feed a card if auto-feed is on, or scan a card already held instead of feeding a second one). The connect self-test's sensor-blocked refusal (`{"error":...,"module":N}`) reuses the same body in its own toast (`use-serial.tsx`, `SENSOR_BLOCKED_TOAST_ID`) instead of disconnecting: "Mark cleared" re-reads IR and, once every module is clear, reruns the connect test on the same transport.
- USB auto-connect is a per-device flag (`devices.auto_connect`, toggled from the Connection panel at the top of the calibration Modules & Routing page). Web Serial only lets a page open ports it was already granted, and a board's identity only comes from its firmware after the port is open, so `useSerialAutoConnect` (mounted once in `AppProviders`, active only while some org device has the flag) hands every granted, unopened port to the standby station, from `getPorts()` on load and from the `connect` event on plug-in, one at a time. `use-serial.tsx`'s `connectPort` opens it with `autoConnect: true`, and `openTransport` quietly disconnects once the port resolves to a device without the flag, before any self-test; with the flag, the usual lease, setup check and connect self-test run so the sorter ends up ready. Ports are skipped while `isFlashInProgress()` (a flash reboots the board mid-write), and a board must be connected by hand once per browser to be granted. Bluetooth can't do the same for a fresh page load: `navigator.bluetooth.getDevices()` and `watchAdvertisements()` are still behind Chrome flags. So for auto-connect devices, when a Bluetooth link drops unexpectedly, `use-serial.tsx` keeps the tab's `BluetoothDevice` and retries `gatt.connect()` (no user gesture needed) with backoff up to 30 s, until it reconnects, something else connects to that station, or the flag is turned off. When the flagged APIs are present, `useSerialAutoConnect` also watches advertisements from granted devices and connects them, limited to Bluetooth devices this browser previously bound to an auto-connect sorter (`ble-device-map.ts`, keyed by the per-origin `BluetoothDevice.id`, written on each bind), so it never connects unknown devices just to identify them.
- Web Bluetooth's `gatt.connect()` can resolve and then drop the link before service discovery ("GATT Server is disconnected. Cannot retrieve services"), mostly on Windows and right after an ESP32 boots, so `BluetoothTransport` (`features/scanner/lib/transports.ts`) retries connect plus service/characteristic lookup `BLE_CONNECT_ATTEMPTS` times with a growing delay before reporting failure.
- The ESP32-S3 release build (`.github/workflows/firmware-release.yml`'s `FQBN`) pins `FlashMode=dio`. The core's default QIO bootloader hangs on some clone boards' flash chips (a Hosyond N16R8 boot-looped with `rst:0x7 (TG0WDT_SYS_RST)` and a ROM `Saved PC` right after `entry`), and DIO works on every quad-flash S3.
- The `legacy` servo channel layout (module 1 at PCA9685 channel 4, capped at 3 modules) is deprecated: there's no layout picker, and every new device is `standard` (channel 0). Devices already on `legacy` keep working at their offset, since their hardware is physically wired that way, and see a banner whose "Update to Standard" button (`ChannelLayoutUpgradeButton`, behind a "have you rewired it" confirmation) is the only way to change it. `PUT /devices/:guid` rejects any `channelLayout` other than `standard`, and calibration import ignores the file's layout, so nothing can move a device onto `legacy`.
- The Arduino preprocessor writes a prototype for every sketch function near the top of `main.ino`, above any struct defined later, so a function whose signature uses a sketch-defined struct (e.g. `captureConfig(StoredConfig&)`) needs its own prototype right after the struct. The preprocessor skips functions that already have one.
- The firmware has no concept of a "bin" — the web app owns the bin→(module, direction) mapping (`shared/interfaces/bin-routes.interface.ts`) and resolves it before ever sending a serial `route` command.
- Every setting on the calibration pages, toggles included, is staged as a draft and saved through the page's `SaveBar` (with `UnsavedChangesGuard`), never on change. The device toggles on Modules & Routing (auto-connect, self-test on connect, pipelined feed) go through `useDeviceTogglesDraft`, committed alongside module count, bin routes and bin heights. View-only switches that aren't saved (the per-module raw pulse view) are the exception.
- New-device setup: `devices.setup_completed_at` is null until the setup wizard is finished or skipped (migration `0050` marked every pre-existing device as done). For a bound device without it, `use-serial.tsx` skips the connect self-test and `SetupWizardProvider` (`features/calibration/api/use-setup-wizard.tsx`, mounted per `StationScope`) opens `DeviceSetupWizard` (`features/calibration/components/device-setup-wizard.tsx`): intro, module count, every servo position of every module (`SETUP_SERVO_POSITIONS`), an IR sensor check, feeder speed, then the self-test. Because the skipped connect test is what normally runs the pre-test hooks, the wizard sends `setChannelOffset` itself before moving servos. It can only be left through Finish or Skip, both of which set `setupCompleted`. Anyone can reopen it from the calibration page's help (?) menu; platform admins can force it again from Configuration > Force setup wizard, and `PUT /devices/:guid` rejects `setupCompleted: false` from non-admins.
- Every UI control that sends a serial command requires a passed self-test on the current connection: `useSerial().isReady` turns true only on the firmware's `test_complete`, and resets on disconnect and at the start of each test. The exception is a device with `devices.test_on_connect` off (the Connection panel's "Run self-test on connect" toggle): on connect, `syncWithoutTest` still runs the pre-test hooks (channel offset, servo and feeder calibration), sends `neutral` (bottoms and side paddles closed, pushers neutral, feeder stopped) and then sets `isReady` without the test. The one exception is servo calibration while a sorter is completely uncalibrated (`canCalibrate` in `use-calibration-page.ts`), since `handleTest` refuses to run on default calibration. Automatic config syncs and the scan pipeline's routing aren't buttons and aren't gated this way (routing checks `isReady` itself). The admin Kit testing tab (`/app/admin/servos`, `KitTestBench`) is also exempt: it's for checking bare kit boards and loose servos, which usually can't pass the self-test, so it connects with `skipAutoTest`, records the self-test as a result rather than a gate, and drives raw channels through `sendRawCommand`. Its session (servo pass/fail tally, which IR sensors have read both a card and no card, self-test result) lives only in component state and is exported as a copyable kit report. The admin Device playground (`/app/admin/device`, platform admins only, `features/admin/components/device-playground.tsx`) is the other deliberate exception: it only needs a connection, since it exists to send any protocol command (including `test` and `setChannelOffset` themselves). Its command catalog is `DEVICE_COMMANDS` (`lib/constants/device-playground.ts`), one entry per protocol command with typed fields and a payload builder, so a new firmware command gets an entry there plus a description under `admin.devicePlayground.commands`. Every send goes through `useSerial().sendRawCommand`, which shares the route busy lock so it can't interleave with another command's reply. Since a connected sorter keeps scanning off the scanner page, hardware-editing pages (the calibration layout, admin servo tester) are also wrapped in `SessionLock` (`features/scanner/components/session-lock.tsx`), which shows a warning banner and makes the page `inert` while `useIsSessionActive()` (the session timer running) is true for the active station.
- The scanner's Bin Levels meter (`BinStatusMeter`) is laid out like the machine, not in bin-number order: one row per module in `BIN_SLOTS_PHYSICAL_ORDER`, then the bottom bins, via `buildBinLevelLayout` (bins without a route fall in at the end, two per row). It uses the stats-panel style (one bordered panel, bins as compact one-row `BinLevelCell`s): label and catch-all tag on the left, `count/capacity` on the right, the cell background filling from the left as the fill indicator (tinted by status), and an icon at `BIN_LEVEL_WARNING_PERCENT`/`BIN_LEVEL_FULL_PERCENT`, never color alone. The whole cell is a button that opens the same empty confirmation as before; the panel collapses to a one-line `summarizeBinLevels` summary (remembered per browser); and a cell flashes when `useScannedCards().lastRoutedBin` points at it.
- The firmware's pusher directions are mirrored from the front of the sorter: a `"left"` push lands on the physical right, so bin 1 (module 1, `"left"`) is top right. Bin layouts in the UI render through `BIN_SLOTS_PHYSICAL_ORDER` (`lib/constants/calibration.ts`); never change the default routes to "fix" the display.

### Discord bot

- `packages/bot` is one public bot shared by every server. Slash commands are registered globally only (or to `DISCORD_DEV_GUILD_ID` in dev), never per guild on join: doing both showed every command twice. On startup the bot clears any leftover guild-scoped commands. Each guild maps to exactly one org via `org_settings.discord_guild_id`, set by `/link <code>` (8-char code from Settings, 10 minute TTL). Linking an org to a different guild, or the bot being removed from a guild (`GuildDelete` calls `POST /bot/unlink`), clears every Discord channel/thread reference for that org through `clearOrgDiscordReferences`, so notifications never go to a server the org left.
- The Integrations page (`/app/integrations`, `features/integrations`, `routes/integrations`) holds Discord linking, the channel pickers and collection overrides, the scan toggle and test buttons (moved from Settings), and notification rules. There's deliberately no separate overview of every channel in use: each picker already shows its channel. Channel names, categories and the bot's missing permissions come live from the bot's `GET /guilds/:guildId` (`notify-server.ts`, via `fetchDiscordGuild`), since the app only stores channel ids. Notification rules (`notification_rules`, per org and game, built with the bins `RuleGroupEditor` like sound rules) each target one channel of the linked guild: on every saved scan, `postMatchingNotificationRules` (`lib/notification-rules.ts`, called from `notify-card-scanned.ts` whether or not "every scan" is on) evaluates them server-side, off the scan path: `notifyCardScanned` only enqueues a job on `lib/scan-notification-queue.ts` (run after the response via `setImmediate`, at most `SCAN_NOTIFICATION_CONCURRENCY` at once so a burst can't starve scan saves of DB connections, oldest dropped past `SCAN_NOTIFICATION_QUEUE_LIMIT`), and that job loads settings, matches rules and posts. It posts the card once per matching channel, directly in the channel rather than a thread (only the every-scan feed and its scan-session summary use a thread, "Card Scans", whose id is kept in `discord_scan_thread_id`, and only while `org_settings.discord_scan_use_threads` is on (default true, toggled next to "every scan"; off posts them straight into the channel too); errors and alerts always post straight into their channel, so `discord_error_thread_id` is no longer written), with the matched rule names in the footer. A rule's channel is checked against the guild on save (`checkDiscordChannel`), and `/notify` also refuses a channel outside the `guildId` it's sent with, so a rule can never post into another server the bot is in. A free-plan org can have `FREE_PLAN_MAX_NOTIFICATION_RULES` (default 1) notification rules across all games, Business and billing-disabled installs unlimited (`lib/notification-rule-limit.ts`, sent as `billing.maxNotificationRules`), with `NOTIFICATION_RULES_PER_ORG_LIMIT` (100) as a hard cap for everyone. Like sound rules, only `POST /integrations/discord/rules` enforces it, so a downgraded org keeps the rules it has. A rule can also ping one role (`notification_rules.role_id`): the bot lists the guild's roles (excluding @everyone and bot-managed roles) with `canPing` (mentionable, or the bot has Mention Everyone), `checkRuleTargets` validates both channel and role on save, and `/notify`'s `pingRoleIds` becomes the message content with `allowedMentions` limited to exactly those roles, so a post can never ping anything else. When several rules match into one channel, their roles are combined into one post. Unlinking nulls every rule's `channel_id` and `role_id` (the rules stay, disabled in effect, until a channel is picked again). Rules store field keys, so `applyFieldRenames` rewrites them, and `purgeOrgData` deletes them.
- Platform stats posts: platform admins pick a Discord server, a channel and which stats to post on Admin > Discord stats (`/app/admin/discord-stats`, `PlatformStatsManager`), saved to the single `platform_stats_settings` row (written only through `db`, like `scan_stats`). Nothing in the app or bot schedules them: `scripts/post-platform-stats.ts` (`node packages/server/dist/scripts/post-platform-stats.js`, run by a Coolify scheduled task on whatever cron) and the page's "Post now" button both call `postPlatformStats` (`lib/platform-stats.ts`), which computes only the selected `PLATFORM_STAT_KEYS` (`shared`) and posts one embed straight into the channel through the bot's `/notify` with the saved `guildId`, so it can't land in another server. The script exits 0 when nothing is configured and 1 when the bot couldn't post. Users and organizations come from `AuthProvider.countUsersAndOrganisations`, so both auth modes work; scanned cards come from `scan_stats`, so deletes never lower them. Since the script is its own process, no stat can read in-memory state (device leases, scan locks). The server picker lists every guild the bot is in from the bot's `GET /guilds`, and saving re-checks the channel and the bot's permissions against `GET /guilds/:guildId`. A new stat needs a key in `PLATFORM_STAT_KEYS`, a loader in `lib/platform-stats.ts`, a label in `PLATFORM_STAT_LABELS` and `admin.platformStats.stats` translations.
- The bot has only two commands, `/link` and `/stats`. Every channel choice lives in the app: the Integrations page's channel pickers (`PUT /integrations/discord/channels`, which takes `scanChannelId` and/or `errorChannelId`, org-wide or for one `collectionGuid`; orgs can have unlimited collections, so the page only lists collections that already have an override and adds new ones through a searchable picker, never a row per collection, owners and admins only, checked inline rather than with `requireOrgRole` since a 403 signs the web client out) and notification rules. Pickers accept text and announcement channels and grey out any where the bot is missing a permission (`NOTIFY_CHANNEL_PERMISSIONS`, `bot/src/lib/constants.ts`), and the server re-checks the channel against the linked guild on save, so a missing permission fails at setup instead of silently at scan time. Removing commands needs no cleanup in Discord: the bot overwrites its global command list on every start.

### Web structure

- Bulletproof React, feature-first: `features/<name>/{api,components,lib}` (current features include `bins`, `calibration`, `cards`, `collections`, `companies`, `games`, `notifications`, `scanner`, `storage`). Cross-feature code only belongs in the top-level `components/`, `hooks/`, `lib/` — not a feature folder.
- Routing is React Router v7 under `app/routes/` (`app/*` for the authenticated app shell, `build/*` for the in-app hardware build guide, plus `landing`/`auth`). Every build-guide section (Parts groups, Wiring subsections, Assembly phases and individual steps) has a stable id from `features/build/lib/anchors.ts` and an `AnchorLinkButton` that copies a `#hash` link for support. `useScrollToHash()` retries for a few frames on load because sections render late and the Parts accordion may be closed (kit mode), which `bom.tsx` opens for any `#parts-*` hash. Step anchors are `step-<key>`, never the bare step key, since that's already the checkbox's id.
- `@/*` resolves to `packages/web/src/*`.
- All API calls go through `lib/api/client.ts` (`apiGet`/`Post`/`Put`/`Delete`/`PostForm`) or feature-specific wrappers under `features/*/api/`, always with `Authorization: Bearer <token>` — never cookies.
- Toasts render through the single `Toaster` mounted in `main.tsx` (`components/ui/sonner.tsx`, `richColors` with per-type `--toast-*` tokens in `index.css`). `NeonAuthUIProvider` renders its own unconfigured sonner `<Toaster />` that would duplicate every toast, so `index.css` hides any `[data-sonner-toaster]` without the `app-toaster` class. Local auth mode has no such provider, which is why the app's own mount lives at the root rather than inside an auth guard. Toast buttons are always right-aligned and grouped together: `index.css` overrides Sonner's `margin-left: auto` on every `[data-button]` (which split `cancel` and `action` apart) and top-aligns the type icon, and custom toast bodies (`jam-toast-body.tsx`, `support-prompt-toast.tsx`) use `justify-end` button rows.
- Keyboard shortcuts all go through `useHotkeys` (`hooks/use-hotkeys.ts`), never a raw `keydown` listener for app-level keys. Every binding is declared in `HOTKEYS` (`lib/constants/hotkeys.ts`), which also drives the `?` shortcuts dialog (`components/keyboard-shortcuts-dialog.tsx`, opened from the footer). One document listener (`lib/hotkeys.ts`) serves every registration, so a two-key sequence like `g s` is never also read as the scanner's `s`. Keys are ignored while typing in a field, holding a modifier, or while any `role="dialog"` (base-ui popovers included) is open. Pass `undefined` as a handler to let the key through when its action is unavailable. Scanner keys are registered in `ScannerControls` and only fire for the active station while its panel is docked on the scanner page. `/` focuses the first visible input carrying `data-hotkey-search`. The card detail panel registers `cardPrevious`/`cardNext` (arrows), `cardCorrect` (`c`) and `cardClose` (Esc, which cancels correcting first); while correcting, the search input and result tiles handle their own keys (`useCardResultKeyboardNav`: Down into the results, arrows move by tile or row, Up from the top row back to the input, Enter in the input picks the first result), and picking a correction stays on the panel instead of closing it. Review mode (`?review=1` on `/app/cards/:scanId`, `CARD_REVIEW_SEARCH_PARAM`, started from the grid toolbar or `r`) walks the grid's current query from its first card: Enter (`reviewAccept`) marks a flagged card as correct (an unflagged one is left alone) and moves on, a correction moves on too unless picked with Shift, and the last card returns to the grid with a toast. `f` (`cardToggleFoil`) sets the scan to the game's first foil type, or back to non-foil, so the order of a game's `foilTypes` in the Games Manager decides which foil it picks. The foil select blurs its trigger when it closes (`onOpenChangeComplete`), since a focused trigger is an ignored hotkey target and would reopen on the next Enter or Space. `f` is also the scanner's feed key, so the panel registers its hotkeys with `HOTKEY_PRIORITY_OVERRIDE`: `useHotkeys`' third argument, where the highest-priority registration with a handler for a key wins and ties go to registration order.
- Settings is laid out like Admin: `app/routes/app/settings/layout.tsx` renders a `SectionNav` (`SETTINGS_SECTIONS`, `lib/constants/settings.ts`) over sub-pages General, Organization, Billing (hosted only), Scanning, Sounds and Integrations. Sounds and Integrations have no top-level nav item of their own; `/app/sounds` and `/app/integrations` redirect into Settings. Link to a sub-page through `SETTINGS_PATHS` (upgrade prompts go to `SETTINGS_PATHS.billing`), never a bare `/app/settings`. The index route forwards to General, or to Billing (search kept) when Stripe's checkout redirect carries `?billing=`, which `useBillingCheckoutReturn` in the layout turns into a toast. Each sub-page holds only a few panels, so a page never gets crowded: a panel is a `SettingsSection` (`components/settings-section.tsx`: heading, optional description, badge and `action`) inside `SettingsSections`. Settings, Account, Admin and Calibrate all render sections flat, with no box: each section draws a top divider (skipped for the first in its container) with spacing, and the heading (description below, `action` at the top right) sits above its controls. Side-by-side title and content columns were tried and rejected as looking odd. The layout comes from `SettingsSectionLayoutContext`, which `SettingsSections` and the Admin and Calibrate layouts set to `flat`, so pages never pick it themselves; anywhere outside those it falls back to a bordered card. Admin managers that used to draw their own box with a header bar (games, announcements, users, card database, card sync) are `SettingsSection`s too. So are the calibrate panels (connection, experimental features, IR sensors, bin routing tests, module count, bin configurations, feeder, module calibration, scan region); `SettingsSection` takes a `dataTour` prop for the guided tour's anchors, since wrapping a section would break its first-section divider rule. The only borders inside a flat section are lists (`rounded-lg border divide-y`, `empty:hidden`). A component that owns a whole panel (e.g. `SoundRuleList`, `NotificationRuleList`) renders its own `SettingsSection`. When a section grows too big for one page, split it into another sub-page rather than stacking more panels.
- Forms always use React Hook Form + a Zod resolver — never a hand-rolled `useState`-per-field form.
- UI conventions (app, not marketing pages):
  - Status color comes only from the theme tokens in `index.css`: `success`, `warning`, `info` and `destructive`, each with a base (dots, icons), `-strong` (fills behind white text), `-foreground` (text), `-muted` (tinted background) and `-border` shade. Never use Tailwind's raw `green-*`/`amber-*`/`blue-*`/`red-*` for status. The toast colors alias these tokens. Raw palette colors are only for data (MTG color swatches, avatar palettes, wire colors in the build guide, the env banner).
  - Notes, warnings and errors inside a page use `Callout` (`components/callout.tsx`, variants `neutral`/`info`/`success`/`warning`/`error`); full-width bars use `AlertBanner`, and their buttons use `ALERT_BANNER_ACTION_CLASS`.
  - Text sizes: `text-sm` body, `text-xs` for secondary text, labels and logs, and `text-2xs` (a theme token, 10px) for dense captions: uppercase stat labels, help text under controls in the scanner and calibration panels, count bubbles, avatar initials, thumbnail captions and diagram labels. No arbitrary `text-[Npx]` sizes; when tightening a dense panel, step down the scale (`sm` to `xs` to `2xs`) rather than inventing a size. Text inputs are the exception: `Input`, `Textarea`, the combobox chips input and the OTP input are `text-base` below `md` (and `md:text-xs/relaxed` above), since iOS Safari zooms the page into any focused field under 16px. Don't override an input's text size on mobile-reachable pages.
  - Secondary text is `text-foreground/70`, and no text goes below 70% opacity (de-emphasize further with size or weight instead). The only exception is disabled controls. `text-muted-foreground` is left to the shadcn primitives in `components/ui` and placeholders.
  - Every panel is a `SettingsSection` (flat in Settings, Account and Admin; see the Settings bullet); items nested inside one use `rounded-md border`, with `bg-muted` for stat tiles, and lists use one bordered, divided list. Page titles are `font-heading text-lg font-semibold`; small uppercase sub-labels are `text-xs font-medium uppercase tracking-wide text-foreground/70`. A form or control's field label is always `text-xs font-medium` at full color (what `Label`/`FieldLabel` render; hand-rolled labels in the calibration and scanner panels match it), with its help text below in `text-2xs text-foreground/70`.
  - A labelled slider (calibration and similar) is `SliderField` (`components/slider-field.tsx`): label, optional `description` shown behind an info icon rather than as a paragraph, current value, slider, and a `children` slot for extras such as `RawStepperRow`. Empty lists use `EmptyState` (`components/empty-state.tsx`, `size="compact"` inside panels), never a bare line of text.
  - Icons inside shadcn primitives (`Button`, menu and select items) are sized by the primitive, which only applies its size to SVGs without a `size-*` class: leave those icons unsized or use the `size={N}` prop, never a `size-*` class, or the icon grows past what the primitive intends. Standalone icons use `size-3` (micro), `size-3.5` (beside `text-xs`), `size-4` (default) or `size-5` (prominent).
  - Motion is short and functional: `animate-in` fades/slides of 200-500ms for things that just appeared (newly scanned grid cards within `NEW_CARD_ANIMATION_WINDOW_MS`); no page or route transitions, so pages, the card detail panel and empty states appear instantly, always with `motion-reduce:animate-none` on anything that moves.
  - Small trends use `Sparkline` (`components/sparkline.tsx`): one series, a de-emphasized line with the latest point in `primary`, a hover tooltip per point, and an `aria-label`. The scanner stats' Cards / hour tile shows scans per minute over the last `SCAN_RATE_BUCKET_COUNT` minutes from `useScannedCards().recentScanTimes` (session-local, cleared with the session timer).
  - Right-clicking a card in the grid opens `CardContextMenu` (`components/ui/context-menu.tsx`, base-ui's context menu styled like the dropdown menu): open, select, mark as correct (flagged cards only), a foil submenu (`useFoilOptions`, shared with the scanner's foil picker and the detail panel), copy name, and remove. Actions on a grouped-duplicates tile apply to every scan in the group. The same actions (minus Select) are on mobile: for members (`canEditCards`), holding a `MobileCardTile` (`useLongPress`, which also swallows the click that follows) opens `MobileCardActionsDrawer`, with foil as inline buttons since mobile drawers avoid popovers. Both surfaces get their behavior from `useCardActions`, so add new card actions there.
  - The card grid has a per-browser size setting (`CARD_GRID_DENSITY_CLASS`: compact, comfortable, large).
  - Corner radius follows one scale (theme `--radius` 0.625rem): `rounded-xl` for floating overlays (dialogs, drawers, the mobile nav island), `rounded-lg` for containers (panels, lists, popovers, callouts, card tiles, log and code blocks, the save bar), `rounded-md` for controls and anything nested inside a container (buttons, inputs, chips, thumbnails, stat tiles), `rounded-sm` for tiny inline bits (inline code, kbd, text-line skeletons, hover highlights on text rows), `rounded-full` for pills, dots, avatars and progress bars. Never Tailwind's plain `rounded` (a fixed 4px that ignores the theme). Something padded inside a rounded box takes the next step down, e.g. the grid card tile is `rounded-lg p-1` around a `rounded-md` image.
  - Loading content shows skeletons (`CardTileSkeletonGrid`, `CardDetailSkeleton`, `ListSkeleton`, or `Skeleton` directly); `IconLoader2` spinners are only for an action in progress (inside its button or an inline status line) and page-level bootstrap screens.
- Nothing auto-saves. Every settings control (switches, selects, pickers, reordering) edits a draft that's saved through the page's single `SaveBar` with an `UnsavedChangesGuard`. Draft forms take server data through `values` with `resetOptions: { keepDirtyValues: true }`, so a refetch (e.g. after a dialog adds a rule) updates untouched fields without clobbering unsaved ones, and saving sends only what changed. A page whose panels live in several components shares one form: `DiscordIntegration` wraps its sections in a `FormProvider` (`useDiscordSettingsDraft`), the General and Scanning pages both use `useOrgSettingsDraft`, Sounds uses `useSoundRulesDraft`, and Organization combines the rename and member-role forms behind one bar. Discrete actions stay immediate: dialogs with their own submit, deletes, uploads, invites, test buttons. `PrimaryColorPicker` previews the draft color live and restores the saved one when it unmounts.
- Bin rules export/import (`features/bins/lib/bin-rules-export.ts`, schema in `schemas/bin-rules-export.schema.ts`) is versioned JSON of a preset's bins only (not its auto-assign/scan-only/repack settings). An import always creates a new preset through `POST /bins`'s `initialBins`, never overwrites one, and is rejected if it was exported from a different game. Format 1 files predate catch-all rules, so `parseBinRulesExport` empties a catch-all's rules when importing one.
- Chaos sort is a per-preset mode (`bin_sets.is_chaos_mode`), exclusive with auto-assign, scan-only, repack and alphabetical, toggled from the bins page's mode panel and saved with `PUT /bins/:guid/chaos`. It's Business-only: `lib/chaos-sort-access.ts` (`chaosSortAllowedForPlan`, true when billing is disabled) is sent to the client as `billing.chaosSort`, which locks the toggle with a Business badge and upgrade link, and `PUT /bins/:guid/chaos` refuses to turn it on for a free-plan org. Like sound and notification rule limits, only turning it on is enforced, so an org that downgrades keeps a preset already in chaos mode (and can still turn it off or change its bin size). Routing ignores rules: `evaluateChaosBin` (`shared`) sends each card to the lowest-numbered enabled, non-catch-all bin that isn't full (`isBinFullLocally`, so pending routes count), the low-match catch-all check still runs first. Once every one of those bins is full (`areAllChaosBinsFull`), `addCard` pauses instead of sending the card to the catch-all and the scanner steps through them in bin order (`fullBins`), opening `EmptyBinToLocationDialog` once per bin with its own location choice; each confirm empties that bin (`emptyNextFullBin`), and the last one resumes, rescanning the held card. "Not now" leaves scanning paused with the remaining bins still full, and the next resume asks again if every bin is still full. `bin_sets.chaos_bin_size` (null = fill to the calibrated size, set as "Cards per bin" under the chaos toggle, max `CHAOS_BIN_SIZE_MAX`) caps every non-catch-all bin in chaos mode: `useComputedBinFillLevels` uses the smaller of it and the physical capacity, so routing, `isBinFullLocally` and the Bin Levels meter all treat a bin as full at that count. The server's `findFullBin` still only checks physical capacity. Its purpose is inventory, though recording a location works in every mode: both the Bin Levels empty confirmation and the "Bin N is full" pause (`binLimitReached`, `resolveBinLimit`) use `EmptyBinToLocationDialog`, defaulting to "Don't record a location" outside chaos mode (`preferLocation`). It picks (or creates) a storage location and sends `locationGuid` + `collectionGuid` with `POST /bins/bins/:binNumber/empty`. Before the bin's `last_emptied_at` moves, `assignBinToLocation` (`lib/storage-locations.ts`) gives every scan in that bin since the last empty `collection_cards.location_id` and a `location_position` continuing after the location's current highest, ordered by scan time, since cards stack in a bin in the order they were sorted. Unmatched scans in the same bin are physically in the stack too, so they take a position number without being stored themselves. Storage locations are Business-only (`lib/storage-access.ts`, sent as `billing.storage`, read on the web through `useStorageAccess`): a free-plan org can't create a location (`POST /storage-locations`) or record a bin into one (`locationGuid` on the empty-bin route), and the empty-bin dialog drops its location picker for a plain reset with an upgrade note. Like the other Business limits, a downgraded org keeps what it has: it can still browse, search, rename, delete and remove cards from its existing locations. Locations (`storage_locations`, one flat list per org, unique names, RLS like the other org tables, in `bootstrap-local.sql`'s grants and `purgeOrgData`) are managed on the Storage page (`/app/storage`, `STORAGE_PATH`), which lists each location's cards in position order (`GET /storage-locations/:guid/cards`, card JSON without `raw`). Deleting a location is soft and keeps each card's location and position, so a restore puts the stack back; reads ignore deleted locations. The card detail panel and mobile drawer show a card's location (`CardStorageLocationSection`, `GET /collections/:guid/cards/:scanId/location`). A card taken out of its box (sold, put in a deck) is removed from the location from the Storage page's list or the card's Storage section (`DELETE /storage-locations/:guid/cards/:scanId`), which clears its location and position but keeps it in the collection. Positions never renumber, so deleting or removing a card leaves a gap where it was. The Storage page's search (`GET /storage-locations/search?q=`) finds stored cards by name across every location, up to `STORAGE_SEARCH_RESULT_LIMIT`, and each location's total value is summed server-side with the org's price source (`loadLocations`, reusing `cardPriceSql`). Not built yet: pick lists, a recount for when a stack is disturbed, and storing a stack's facing direction.
- The catch-all bin has two optional settings. "Send low matches here" is a match percent threshold in `bins.low_match_percent` (`BinConfig.lowMatchPercent`). `findLowMatchCatchAll` (`shared`) is checked first in `resolveMatchedBin`, so a scan below the threshold goes to the catch-all in every mode (alphabetical and repack included), ahead of override bins, and auto-assign skips it. Chaos, repack and alphabetical modes still send overflow and leftover cards to the catch-all, so in those modes the bin panel keeps the catch-all toggle (on any bin) and the catch-all's threshold editable, while every other bin only shows its disable toggle. Such a scan is still saved as a normal matched card (it shows in the grid) with `collection_cards.needs_review` set, the same flag OCR-only matches get, so it counts toward "Needs attention" until it's corrected or marked as correct. The catch-all's own `bins.rules` are override rules (rules mode and auto-assign only, never `needs_review`): a catch-all with any conditions counts as an override bin (`isOverrideBin`), so a card matching them goes there even when another bin's rules match, e.g. pulling a stray colored card out of a colorless sort. Auto-assign never claims a bin for a card the catch-all's rules take (`matchesCatchAllRules`). The threshold used to live in the catch-all's rules as a single `matchPercent` `lt` condition: migration `0090` moved it to the column, and `parseLegacyCatchAllThreshold` converts old audit snapshots on revert (`fromLegacyCatchAllRules`, also used by `POST /bins` for imports) and format 2 rules exports on import (format 3 carries `lowMatchPercent`/`overridePriority`). Format 1 files predate catch-all rules, so their catch-all rules are dropped. Before rules existed on the catch-all, migration `0078` emptied them, and the panel clears the rules, threshold and priority whenever a bin is switched to or from catch-all, as do the mode-switch helpers that make a bin the catch-all.
- Override priority: `bins.override_priority` (`BinConfig.overridePriority`, 1 to `OVERRIDE_PRIORITY_MAX`, null = none, only kept on override bins and the catch-all; "Priority level" in the UI) decides which override wins when several match a card in `evaluateCardBin`: 1 is the highest, so the lowest number wins. Overrides that share a level send the card to the emptiest of their bins, through `evaluateCardBin`'s optional `cardsInBin` callback (the scanner passes `countCardsLocally`: the bin meter's count plus routes still pending). Overrides without a priority come after every leveled one, in configuration (bin number) order with no emptiest tie-break, so presets from before levels existed route exactly as they did. `sortOverrideBins` gives the same order, which the bin panel shows under the input, with tied levels marked emptiest first.
- A bin can cap how many copies of one printing it takes (`bins.max_copies`, null = unlimited, always null on the catch-all): `evaluateCardBin`'s optional `copiesInBin` callback skips a matching bin (override or not) once it holds that many cards with the same `PlayingCard.id` since its `lastEmptiedAt`, so the card falls through to the next matching bin, then the catch-all. The scanner counts from the same `binContentsRef` repack mode uses (`use-scanned-cards.tsx`), loaded whenever the preset is in repack mode or any bin has a copy limit, and appended to optimistically as each card is routed so back-to-back copies are counted before their saves land. The server never evaluates rules, so it doesn't enforce the cap.
- Repack mode can sift cards out (`bin_sets.repack_sift_rules`, a `BinRuleGroup`, null or empty = off, built with the `RuleGroupEditor` in the repack panel): `evaluateRepackBin` sends any card matching it to the sift bin, the lowest-numbered enabled non-catch-all bin (`getRepackSiftBin`, normally bin 1), ahead of pack building, and leaves that bin out of the packs, so every other bin builds packs from the rest. Scanning stops once every pack bin (`getRepackPackBins`: enabled, non-catch-all, minus the sift bin) has met its pack limit (`areAllRepackPacksComplete`): `addCard` pauses as soon as a routed card completes the last pack (before its route is sent, so no further card is fed), and again for any later card that would only go to the catch-all, holding it. Either way it opens the same step-through empty dialog chaos mode uses (`fullBins`, `emptyNextFullBin`), one pack bin at a time, and the last one resumes. Sift rules store field keys, so `applyFieldRenames` rewrites them too.
- A bin can be disabled (`bins.is_disabled`, never true on the catch-all; `toIsDisabled` on the server forces that, and making a bin the catch-all or the scan-only bin turns it back on). Every routing mode skips it in `shared`: `evaluateCardBin` and `evaluateRepackBin` pass over it, and `getAlphabetBins` leaves it out, so alphabetical mode spreads the letters over the remaining bins. Auto-assign never claims it. Its rules, copy limit and override flag are kept while disabled. `PUT /bins/bins/:binNumber` keeps the current value when `isDisabled` is omitted, since callers like auto-assign and the catch-all helpers don't send it. The bins page makes cards selectable in repack and alphabetical modes too, where the panel shows only this toggle.
- Alphabetical sort is a per-preset mode (`bin_sets.is_alphabet_mode` + `alphabet_pass`), exclusive with auto-assign, scan-only and repack. It ignores bin rules entirely: `evaluateAlphabetBin` (`shared/evaluate-bin.ts`) reduces `PlayingCard.name` to a letters-only sort key (accents stripped, Æ as AE, spaces and punctuation dropped) and gives each non-catch-all bin one letter, in bin-number order, offset by `pass * binCount`. `bin_sets.alphabet_prefix` (empty by default) narrows it to names whose key starts with that prefix, binned by the character right after it, so sorting the A pile uses prefix `A` and bins AA, AB, AC...; names that don't start with the prefix, or are exactly the prefix, go to the catch-all. Users never type a prefix: the Bins panel's Sort deeper menu lists the current pass's letters and drills into one of them, and `getNextAlphabetStep`/`getPreviousAlphabetStep` step through a pile's passes and then on to its sibling pile (A's last pass leads to B, AB's to AC), which both the panel and the scanner's `AlphabetPassControl` follow. (`alphabet_depth` from migration 0055 was dropped again in 0056.) It reads `name` directly rather than a rule field because `fieldDefinitions` are admin-configured and may not include a name. Changing the pass or prefix (`PUT /bins/:guid/alphabet`) marks every bin in the preset as emptied, since the user has physically cleared them to start the next letters.
- The Vite dev proxy rewrites `/api/*` → `http://localhost:3001/*`; server routes are registered without an `/api` prefix to match (`app.route("/collections", ...)`, not `/api/collections`).

## Code style

Don't add code comments. Code should be self-documenting through clear naming and structure; when something genuinely non-obvious needs recording (a hardware quirk, an ordering constraint, a protocol detail), put it in this file instead. Lint directives like `eslint-disable` are also avoided: restructure the code (e.g. a latest-values ref for an effect that should only re-run on some inputs) rather than suppressing the rule.

Types, interfaces and constants never live in component, hook or route files, even when used only once. In `web`, they go in `lib/interfaces/*` and `lib/constants/*` (component prop types included); in `server`, in `src/lib/interfaces/*` and `src/lib/constants/*`; anything shared by both goes in `shared`.

Never use em dashes, in code, comments, commit messages, or chat responses. Use a comma, colon, or period instead, or split into two sentences.
