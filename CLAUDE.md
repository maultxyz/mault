Tests run in Build Check (`build-check.yml`): server, shortener and tutorials `tests/*.test.ts` (node:test), web `src/**/*.test.{ts,tsx}` (Vitest, own `vitest.config.ts` so tests skip the PWA/Tailwind plugins), and the hardware-free Python Pi suites above. CI uses Node 26 and Python 3.13; Pi service rendering tests also require Node 26. These checks do not validate physical USB/GPIO motion or cameras. Type-check via the `web` build (`tsc -b`) and editor diagnostics. See `CONTRIBUTING.md` (migrations) and `README.md` (env, Neon, self-hosting).

## Every change: keep all surfaces in sync

The product ships on three surfaces that must behave the same:

- **Desktop:** the web app at `md` and up, also loaded unchanged by the Electron shell (`packages/desktop`).
- **Mobile web:** the same web app below `md` (`useIsMobile`, `max-md:` styles, `Mobile*` components). It mirrors the Expo app's exact layout and flow (tabs, screen structure, sheets, step order), built from the web's desktop components, never native-looking stand-ins. Anything added to the Expo app also lands on mobile web in the same task, and mobile web shows nothing the app lacks (web-only features stay at `md` and up).
- **Mobile app:** the Expo app in `packages/mobile`, a separate React Native codebase.

Scanning also has a **headless Pi host execution mode** (`piHost`): the API owns the camera and sorter and must continue scanning while browsers are closed. Include this mode in every feature assessment and per-surface summary; it uses the existing web UI rather than a separate UI surface.

For every change (feature, fix, copy, setting, API):

1. Work out how it affects each surface, including the mobile app when the request names only one.
2. Make it on every surface it applies to in the same task, or say which surface was left out and why.
3. Put logic both apps need in `shared` instead of duplicating it. Serial reply matching, the busy guard and the route queue live in `shared`'s `SerialSession` (web `use-serial` and mobile `SorterLink` wrap it); both `CloudTransport`s extend `SorterLinkConnection`.
4. Add every new string to all locales on every surface: web `locales/{en,de,fr}/*.json` and mobile `locales/{en,de,fr}.json`, with identical keys.
5. Keep server and API changes compatible with mobile app versions already in the stores (store releases lag web deploys).
6. Meet WCAG 2.2 AA (the ADA target) on every surface; see Accessibility. A change that isn't accessible isn't done.
7. End with a per-surface summary: changed, unaffected, or not done.

### Shared scan feature requirements

- New scan decisions belong in `packages/shared`: extend `runScanWorkflow`, `runScanDisposition`, identification helpers and scan plans as applicable; never implement a common decision only in a React hook or copy it into a separate Pi algorithm.
- Keep camera access, inference execution, serial/GPIO commands, HTTP, runtime state and UI effects in adapters; camera/serial tunnels do not execute browser feature logic for the host.
- Carry new scan settings and required inputs through shared types and persistence into web, native and host contexts; expose new host state through org-scoped session snapshots/events so reconnecting browsers observe the authoritative session.
- Preserve host execution without browser callbacks, exclusive hardware ownership and confirmed route/save ordering; test applicable USB and built-in GPIO behavior when transport or motion changes.
- Verify shared decisions and affected adapters, including headless execution and reconnect/settings behavior where relevant; document unsupported hardware/platform capabilities and the reason instead of silently skipping the Pi path.
- Follow the feature checklist in [CONTRIBUTING.md](CONTRIBUTING.md#shared-scanning-features-and-pi-host); ordinary UI/API changes should remain shared without adding Pi-only forks.

## Accessibility (WCAG 2.2 AA, required for every change)

- Web lint runs `eslint-plugin-jsx-a11y` (strict) in Build Check; fix findings, never disable rules. `autoFocus` is only for the first field of a dialog or popover, single-form auth pages and the global search page.
- Every control has an accessible name: icon-only `Button`s (including `TooltipTrigger` renders, tooltips don't name their trigger) take `aria-label`; `SelectTrigger`, `Switch`, `Checkbox`, `Slider` and inputs get a visible `Label`/`FieldLabel` via `htmlFor`/wrapping, or `aria-label`. Generic names (close, clear, remove, copy, retry) live in web `common:a11y.*`. Mobile `Pressable`s set `accessibilityRole`, `accessibilityLabel` and `accessibilityState`; `Button` takes `accessibilityLabel` when its label is a symbol.
- Use native elements (`button`, `a`, `Link`) for anything clickable; a mouse-only wrapper around a keyboard-operable control (shift-click capture) is `role="presentation"`. Never nest interactive elements: put a `Link` in `Button`'s `render` instead of inside it.
- Every routed page has exactly one `h1`: `RouteAnnouncer` reads `#main-content h1` to announce navigation and prefix the document title. Layouts render `SkipLink` and `<main id={MAIN_CONTENT_ID} tabIndex={-1}>`; never nest another `main`. Mobile headings use `accessibilityRole="header"`.
- Status changes that appear without focus moving (scan results, sorter state, save results, errors) are announced through a polite live region (`role="status"`) or toasts; errors use `role="alert"`. Mobile uses `accessibilityLiveRegion`/`AccessibilityInfo.announceForAccessibility`.
- Never convey state by color alone: pair it with text or an icon that has a label. Text contrast is 4.5:1 and icons or borders that carry meaning 3:1 in both themes: status text and icons use the `*-foreground` shades (web `text-success-foreground`, mobile `colors.successForeground`), never the bare `success`/`warning` fills, which fail on light backgrounds.
- Informative images get an `alt` (cards: the card name) and decorative ones `alt=""`/`aria-hidden`; mobile images set `accessibilityLabel` or `accessible={false}`. Charts and canvases have a text alternative (summary or table).
- Drag and drop, hover-only and gesture-only actions need a keyboard or single-tap alternative. Timeouts (auto-close timers) must be pausable or extendable.
- Motion respects reduced motion (the global `prefers-reduced-motion` rule plus `motion-reduce:` on custom animations); never block zoom or disable font scaling (`allowFontScaling={false}`/`maxFontSizeMultiplier` are banned on mobile).

## Architecture

pnpm + Turborepo: `shared` (types, constants, zod schemas, rule engine, `vision.ts`, `serial-protocol.ts`; no build), `server` (Hono 4, Drizzle, Postgres), `web` (React 19 SPA), `mobile` (Expo), `desktop` (Electron shell), `bot` (Discord), `api-docs` (Scalar), `shortener` (optional Hono link shortener, :3003, `pnpm dev:shortener`), `tutorials` (Playwright + Remotion tutorial videos, English only, dev-only, never deployed). One root `.env`. The Vite proxy strips `/api`, so server routes have no `/api` prefix. `docker-compose.yml` is the self-hosted stack.

Neon scales to zero after about 5 idle minutes, so nothing may poll the DB on a timer: `/public/health` (polled by every open tab and uptime monitors) only runs `select 1` while the pool already holds connections, else returns the last healthy result; the bot refreshes its games list daily.

### Auth & RLS

- `AUTH_PROVIDER` is `neon` (default) or `local`, picked in `auth/index.ts`; route code never branches on it. Bearer tokens everywhere, never cookies. Web picks its client at module level from `VITE_AUTH_PROVIDER`.
- Org routes: `requireAuth` -> `requireOrg` (`X-Org-Id` adds `org_id` to the claims) -> `requireRole`/`requireOrgRole`. SSE (`routes/stream.ts`) rebuilds the same claims; without `org_id` every `orgRls` table reads empty.
- User-scoped DB access goes through `authQuery(jwtClaims, tx => ...)`, which switches to the `authenticated` role in both auth modes (the app's own role has BYPASSRLS). Plain `db` only for intentional RLS bypass (sync, webhooks, bootstrap, stats), so org filters stay required in every query. New user/org tables use `.enableRLS()` + `crudPolicy` and need grants in `db/bootstrap-local.sql`.
- Hosted must run `auth.user_id()` in the same statement before `set_config('request.jwt.claims', ...)`: Neon's `pg_session_jwt` loads on first use, and loading it inside the membership check wipes the claims. `DB_ROW_LEVEL_SECURITY=off` disables the role switch on hosted; a database refusing `SET ROLE authenticated` logs a loud error and runs unenforced.
- Impersonation tokens carry the `impersonation_audit` guid as `jti`, valid only while that session is open and the actor is still staff (`lib/impersonation-sessions.ts`, cached 10 s). Routes that create credentials or lasting access (API keys, webhooks, sorter links, stats sync keys, share links, shop catalog links, Discord link codes), change members or billing, or delete org data need `rejectAccountChangesWhileImpersonating`; scanning and hardware use `rejectWhileImpersonating`.
- Never spread a request body into `.set()`/`.values()`: list fields explicitly (`pickCalibrationValues` for feeder and module calibration).
- `ORG_SETTINGS_MANAGER_ONLY_KEYS` (leaderboard listing, Discord scan posts, price source, condition multipliers) are owner/admin only: `PUT /org-settings` refuses a member only when one actually changes (clients resend whole drafts); reads return `canManageOrgSettings`. Discord notification rules are owner/admin only.
- Logs and error reports never carry query strings or SQL parameters (tokens travel in `/stream?token=` and share links): `lib/error-redaction.ts` redacts Drizzle failed-query errors for `console.error`/`console.warn` (`lib/redact-console-errors.ts`) and the tracker, reports send `path` not `url`, the web tracker strips queries, nginx logs `$uri` without referrer. Token-keyed caches register with `hasSecretKeys`. Watch-link guest stream payloads drop `MONITOR_LINK_GUEST_HIDDEN_KEYS`.
- Staff routes: `requireRole(...PLATFORM_STAFF_ROLES)`; card sync, card database tools, plans and developer stay `requireRole("admin")`; web Hardware (serial only) is open to staff. Web gates with `useRole().isStaff`, `AdminGuard`, `adminOnly`.
- A 403 signs the web client out, so owner/admin checks on member-reachable pages are inline.
- Role and membership lookups are cached 10 s (`AUTH_LOOKUP_CACHE_TTL_MS`), collection match scope 60 s, then served stale up to one more TTL while refreshing (`createKeyedCache` `staleWhileRefreshingMs`): a revocation can last 20 s. Empty refreshes drop the entry and null results are never cached (no stale 403 for new members or collections).
- No try/catch in route handlers: `app.onError` returns the JSON 500; `/v1` registers its own `onError` (Scryfall error) before mounting. Catch only to map a specific error to another response.
- Own-auth (`local`): `getOwnAuth()` stays lazy (`auth/local.ts` is imported in Neon mode and `createOwnAuth()` throws in production without `OWN_AUTH_TOKEN_PEPPER`). `LocalEmailProvider.send()` never throws; invite links are captured per request via `inviteCaptureStorage` (AsyncLocalStorage), since own-auth gives the raw token only to the email provider. Local API keys are personal (no `organisationId`) and map to a `{ sub }` session. The first account on a fresh instance becomes platform admin. Password-reset responses stay generic.
- Web Neon calls go through nginx's same-origin `/neon-auth/` proxy when `env.js` has `VITE_NEON_AUTH_PROXY_PATH` (from `VITE_NEON_AUTH_URL` in `docker/web-env.sh`), because Safari blocks Neon's cookies as third-party. The proxy strips `X-Forwarded-Host`/`Port`/`Server`/`Proto` and `Forwarded` from Coolify's Traefik (Neon returns `INVALID_HOSTNAME`; the JWT issuer must stay Neon's origin). Vite dev calls Neon directly.
- Sign-in methods (Neon only): web Account and Expo Profile list/unlink via Neon's `list-accounts`/`unlink-account`; shared `linked-sign-in-accounts.ts` decides order and unlinkability (never the password or the last method). Providers are added only by signing in under the same email; `link-social` fails here (`state_mismatch`, its cookie lands on the wrong origin).
- Neon JWTs allow `NEON_JWT_CLOCK_TOLERANCE_SECONDS` (30 s) skew; a 401 retries once with a fresh token: web `fetchWithAuthRetry` (all `api*` helpers and scan saves) via `refreshAuthTokenRejectedByApi`, which calls `/get-session` itself (the SDK's cached JWT can't be cleared); Expo `apiRequest` via `refreshAccessTokenRejectedByApi`. Raw `fetch` with `getAuthHeaders` doesn't retry.
- The active org lives in localStorage for both providers (own-auth has none; Neon's session lags `organization.setActive`).

### Share links & public pages

- Collection (`/watch`) and storage location (`/shared/storage`) share links are HS256 JWTs (`lib/share-tokens.ts`, `MONITOR_LINK_SECRET`, one issuer per kind), revoked by bumping `monitor_link_version`/`share_link_version`. `/public/*-link` reads use plain `db` and return only `SharedStorageCard` fields. Paths and the `t` param live in `shared`; links show as QR codes (`ShareLinkDialog`, mobile `share-link` modal).
- Prices follow the token's `prices` claim (missing means shown): when off, every public read and the guest SSE go through `pricesForShareLink` (strips `SHARE_LINK_HIDDEN_PRICE_KEYS`, zeroes stats). Never hide prices only in the UI.
- Each collection/location link is a `share_links` row (`lib/share-links.ts`) whose guid is the `jti`; verification rejects revoked rows, revoke-all revokes the subject's rows. Tokens are signed deterministically from the row (fixed `iat`/`exp`), so `GET /share-links?subjectGuid=` (also the Share button's badge) re-signs instead of storing tokens. Tokens without `jti` are checked by version only.
- `purpose` claim: `view` (default, also when missing) or `trade`. Lengths are admin platform settings (`platform_share_link_settings`, `lib/share-link-lengths.ts`; defaults 1 h trade, 1 h monitor without `longShareLinks`, day choices 1/7/30 with it), sent as `/billing` `shareLinkLengths`, enforced at verify time from `iat` (`share-link-policy.ts`), so shortening cuts live links. Requested day counts are clamped, not rejected (store apps send 1/7/30).
- Card share links (kind `card`, `/shared/card/<scan guid>`): view-only, never-expiring (`CARD_SHARE_LINK_LIFETIME_DAYS`, shortener expiry null, any plan) rows keyed by `collection_card_id`, revoked only via the row (survives the re-sort guid rewrite). `POST /share-links/cards/:scanId` returns or issues the link; `GET /share-links/cards?collectionGuid=` feeds the Shared cards tab. The public read is `createPublicCardBrowseRoute` with `collectionCardIds`. `parseShareLinkUrl` ignores them (Expo opens them in the browser). Expo copies via `expo-clipboard`.
- Public card browsing (catalogs, watch, shared storage) is one page (`features/public-cards` `PublicCardBrowser`) over `lib/public-card-browse.ts` (`createPublicCardBrowseRoute`): a link only resolves a `PublicCardBrowseScope` (collections, locations, `inventoryOnly`, prices, optional reads cache; scopes per kind in `lib/share-link-scopes.ts`), never per-link card queries. Link reads aren't cached; catalogs 60 s.
- Shop catalogs (`businessTools`) are never-expiring links (`signRevocableShareToken`, own issuer) reset via `shop_catalogs.share_link_version`; `is_public` catalogs open without a token (`verifyPublicShopCatalog`, rate limited per catalog). Prices follow `shows_prices`, not a claim; `verifyShopCatalogLink` re-checks the plan and drops deleted sources. Card detail is the only public read with scan photos. The shop photo (Business managers) is re-encoded by `sharp` to a 1600 px JPEG, shown only while the org has `businessTools`.
- Share pages (`/watch`, `/shared/*`, `/shop`): nginx serves `share.html` (`scripts/share-page-html.ts`) with SSI from `/public/share-preview<path>` (`lib/share-preview.ts`, cached 30 s), falling back to default noindex tags. SSI upstream (`docker/web-env.sh`): `SHARE_PREVIEW_API_URL`, else absolute `VITE_API_URL`, else `server:3001`; set `SHARE_PREVIEW_API_URL` when `/api` routes straight to the API (hosted Coolify) or previews silently fall back. Only token-less public catalogs are indexable; Vite dev/preview (Pi) serve the plain SPA.
- OG images (`lib/open-graph-image.ts`, sharp, 1200x630 JPEG): `/public/og-image<share path>` (same token, from the cached preview, rate limited per token) and `/public/og-image/pages/<key>.jpg` (shared `MARKETING_OPEN_GRAPH_PAGES`, English only; `?v=` content hash). Text is Figtree outlines via `opentype.js` from `packages/server/assets/fonts` (no system fonts; missing glyphs dropped); stat icons are Tabler paths (`constants/open-graph-icons.ts`, `OPEN_GRAPH_STAT_ICONS`); overflowing stats are dropped, so keep them short. Card art only from `ALLOWED_IMAGE_HOSTS`; shop photos read from storage, never linked. Absolute URLs: `API_URL`, else `WEB_URL` + `/api`. robots.txt keeps `Allow: /api/public/og-image/` (Twitterbot honors `Disallow: /api`). The prerender plugin writes marketing image tags and JSON-LD (`scripts/marketing-structured-data.ts`, kind per `MARKETING_PAGES`).

### Short links

- Optional standalone `shortener` package (own container, not on Pi, unaware of signing). On only with API `SHORT_LINK_BASE_URL` (`shortLinksEnabled`); off, shortener calls are no-ops.
- The API registers signed long paths via `lib/shortener-client.ts` (`SHORTENER_URL`, `SHORTENER_API_SECRET`, in the same transaction) on issue and catalog create/reset/public toggle/restore, deletes on revoke, reset, catalog delete and org purge, and re-registers live links at startup (`startShortLinkStartupSync`).
- Clients share only through shared `buildShareLinkUrl`/`buildShopCatalogLinkUrl` (`shortUrl`, else the long URL). `short_code` is stamped on every `share_links`/`shop_catalogs` row even while off.
- Storage labels print `labelShortUrl` (`storage_locations.label_short_code`, `buildStorageLabelQrUrl`), registered at startup for every row including soft-deleted ones.
- Revocation still holds via `jti`/version checks. `/s/<code>` serves pre-move links, so `/s/` stays out of the PWA navigate fallback; `GET /public/short-link?code=` stays for store apps. Expo's QR scanner reads both forms (`parseShortLinkUrl`, domain from `/public/version` `shortLinkBaseUrl` via `lib/short-link-base-url.ts`, fallback `MOBILE_SHORT_LINK_URL`).
- Custom short links (web Admin > Short links, staff, web-only) are `is_custom` rows: lowercase codes (`customShortLinkFormSchema`, never `RESERVED_SHORT_LINK_CODES` or an app `short_code`) to any http(s) URL, matched case-insensitively. App registration never touches them (`WHERE NOT is_custom`); `GET /public/short-link` never returns them. `/admin/short-links` proxies `/internal/custom-links`, failures are 200 with `reason` (`disabled`, `codeTaken`, `notFound`).

### Trades

- Offers only on trade links (`trade_offers`, `createPublicTradeOffersRoute`). The guest is `X-Guest-Key` (stored hashed); wanted cards are snapshotted at send. Create reads an optional bearer via `optionalVerifiedUserId` (invalid means anonymous, never 401).
- `GET /trade-offers/outgoing` (`requireAuth` only) reads across orgs via plain `db` filtered by the verified user id, guest-visible fields only, never prices; `POST /trade-offers/outgoing/claim` is rate limited per user and never impersonates.
- Offers end `accepted`/`declined` (no soft delete, purged with the org) and emit `trade_offers_changed`. A flagless accept (store apps) hard-deletes wanted cards in the same transaction via `removeTradeOfferWantedCards` (photos, `cards_removed`/`collections_changed`, `cards.deleted` activity); `{ removeWantedCardsWhenPicked: true }` defers it to a pick list (`remaining_pick_scan_ids`).
- Owner review logic lives in shared `trade-offer-review.ts`; `GET /trade-offers` adds `wantedPlacements` (parallel to `wanted`, null when gone).
- The Expo scan tab is the only QR reader (`useScannerQrWatcher`: native on iOS, jsQR on Android live frames), active only while the camera is open and not mid-scan; it opens share links (`parseShareLinkUrl`) and desktop-camera pairing links.
- Optional guest contact: `share_links.requires_guest_contact`, claim `contact: false` (missing means required), enforced on create; blank stored as `""`. Guests price the trade via `POST .../trade-offers/quote` (refused when prices are hidden), priced like owner review, cash added by shared `tradeOfferGuestBalance`.
- Required accounts: trade links via `share_links.requires_guest_account` (claim `account: true`, missing means guests may send); catalogs via `shop_catalogs.reservations_require_account` (store app saves omit it). Create routes return 401 without a verified bearer. Web uses `GuestAccountNotice` and `useGuestAccount`. Owner reads carry `isFromAccount` (`guest_user_id` set): Signed in/Guest badge on web, text in Expo, neither for in-person trades.
- In-person trades (`POST /trade-offers/in-person`, `lib/in-person-trades.ts`): `link_kind` `inPerson`, recorded accepted. Given copies go through `removeTradeOfferWantedCards` with a `priceAtTrade` snapshot, received cards go into the picked collection (its game and lang), cash paid is `given_cash_amount`, added to `wantedValue`. Web (`/app/trades/new`) and Expo (`in-person-trade`) share the schema, `inPersonTradeBalance` and `/trade-offers/in-person/quote`.
- Offers may hold cards, cash, both or nothing: `offered_cash_amount` in the price source's currency at send (`offered_cash_currency`), counted in `offeredValue` only while that currency still matches. Wording: shared `tradeOfferOfferKind` + `TRADE_OFFER_*_KEYS`.
- Card holds were removed; `GET /card-holds` returns an empty list for store apps.

### Other hosted features

- Match validation is hosted-only: with `AUTH_PROVIDER=local` the server doesn't mount `/match-validations`; web (`MATCH_VALIDATIONS_ENABLED`) and Expo hide it.
- Stats sync, hosted: `/stats-sync` key routes (one live `stats_sync_keys` row per org, `mvstats_`, owners/admins) and `POST /stats-sync/push`, replacing `self_hosted_daily_scan_stats` per (org, UTC day) via shared `statsSyncPushSchema`. Self-hosted (`local`): `/stats-sync/connection` (`stats_sync_connections`, plain `db`, key never returned, hard-deleted on disconnect); `startStatsSyncSchedule` pushes `scan_stats` daily totals (all on first sync, then last 7 days) from an in-memory schedule that queries only when due. Only daily counts leave.
- Synced counts never enter `scan_stats` or platform stats; leaderboards include them only with `includeSelfHosted=true` (sent by current clients and the bot unless hidden; missing stays hosted-only for store apps). Entries with `selfHostedScanCount` are tagged Self-hosted.
- What's new merges shared `RELEASE_FEATURE_HIGHLIGHTS` (i18n keys: web `common`, Expo `featureHighlights.*`; media in web `public/feature-highlights/`) with staff `feature_highlights` (web admin only, cached 60 s) via `lib/feature-highlight-selection.ts` (newest first, `FEATURE_HIGHLIGHT_MAX_SHOWN`, `FEATURE_HIGHLIGHT_MAX_AGE_DAYS`). Seen state: `feature_highlight_views` (RLS reads the claim's `sub`; `auth.user_id()` is absent in local databases).
- Uploaded highlight media is `storage:<key>` under `system/feature-highlights/`, presigned on read, mapped back on save; without object storage images are data URLs and video must be external. Videos stay under nginx's 32 MB limit (`FEATURE_HIGHLIGHT_VIDEO_MAX_BYTES`).
- Web shows unseen highlights once per session (`FeatureHighlightsHost`: card at md+, drawer below), skipping scanner/station routes, connected stations, running scans, the onboarding tour and impersonation; Expo shows a `Sheet` only while Home is focused. Dismiss/finish marks all shown seen.
- Timeline (`GET /feature-highlights/timeline`, all published, `nextBefore` cursor, no age window): web `/app/whats-new` (desktop top bar button with unseen count and a 3-newest popover; mobile web More > About), Expo `whats-new`. Highlights render in full inline (web video without autoplay) and are marked seen after half is visible about 500 ms, batched. Search is on-device (text is i18n keys): loads all pages and filters via shared `filterFeatureHighlightsBySearch`; web keeps `?q=`. `?highlight=<id>` loads until found, scrolls, focuses, then drops the param. Expo opens video in the browser until `expo-video` ships.

### Public API & webhooks

- Defined once in `shared` (`schemas/public-api.schema.ts`, `PUBLIC_API_ENDPOINTS`); a new endpoint needs a registry entry, schemas and a handler in `routes/v1/index.ts`, then regenerate `openapi.json`.
- API-key queries run through `apiKeyQuery(orgId, ...)`; a `/v1` query on a new table needs a migration grant and an `api-service-policy-*` policy.
- `/v1` responses follow Scryfall conventions (`object`, snake_case, list envelope), not `{ success, data }`.
- `/v1` is rate limited per key (`createRateLimiter`). `/public/*` has no per-IP limit (no proxy restores the client IP): share links are limited per token (`shareLinkRateLimit`, also guest SSE), claims cached 30 s and shared storage reads 60 s; revoking clears them in-process only. Public metrics and games are cached 24 h with `Cache-Control`.
- Usage logging (`lib/api-usage.ts`) counts `/v1` per key and endpoint (ids normalized, by key hash before lookup) and `/public/*` per route in memory, flushing only while the pool holds connections. 90-day retention; Admin > Developer > API usage. Org purges delete `api_key_usage_daily` before `org_api_keys`.
- Sync API keys (`mvsync_`, `platform_sync_api_keys`) are platform-level: managed at `/admin/sync-api-keys`, `/sync-api` checks `SYNC_API_KEY_PERMISSIONS` per action; it and `/admin/sync` start syncs via `lib/sync-job/start-request.ts`.
- `emit*Webhook` only enqueues; deliveries use `safeLookup` and no redirects. A new event needs `WEBHOOK_EVENTS`, an `emit*` in `lib/webhooks/events.ts` and translations.

### Cards (multi-TCG)

- One adapter per game in `server/src/lib/adapters/<game>/`, registered in `card-search/resolve.ts` and `lib/sync-job/sources.ts`, plus a `Game` row.
- `cards.data` is the source's raw card object (read through `normalizeStored`), one entry per artwork, art through `toPortraitCardImage()`; every `cards.data` write also sets `collector_number`.
- Never hardcode source fields: read through the game's `fieldDefinitions` and `getByPath`/`getCardValue`; game-specific behaviour goes on the adapter (e.g. `rarePrintingSql`).
- TCGTracking (`lib/tcgtracking/`, English only) wraps every source and adapter in `TCGTRACKING_GAMES`: linked cards get `tcgtrackingProductId` (read as `tcgplayerId`), cards the primary lacks become `tcgp-<productId>` fallbacks, and covered fallbacks get `supersededByCardId` and leave matching. Its bulk merge updates the fetched `SyncSourceCard[]` in place, keeping compact match summaries, not every normalized raw card.
- Double-faced cards need `SyncSourceCard.backImageUrl` (sync embeds `back_embedding`, scored alongside the front) and `PlayingCard.backImage` (card detail flip, web and Expo). Today: MTG (`card_faces`), SWU leaders (`BackArt`), Grand Archive flip editions (`other_orientations`).
- English MTG keeps every `default_cards` printing, including ones printed only in another language (Phyrexian, Japanese alt-arts, Elvish, Foreign Black Border), under `en` without `printed_*` fields so names stay English.
- Rules store field keys only; anything new that stores a field key goes in `lib/field-renames.ts`.
- Field definitions come from shared `buildFieldDefinition`; `boolean` always gets `BOOLEAN_FIELD_OPTIONS` (store app versions show a text box). `getCardValue` normalizes `boolean` to `"true"`/`"false"`/null and `date` to `YYYY-MM-DD` (dashes or slashes, time dropped), compared by day.
- Rules evaluate `toRuleCard(...)` with `withScanRuleFields`; never save a `$scan` card. Text comparisons are trimmed and lowercased.

#### Per-game notes

- Sorcery (`api.sorcerytcg.com`): no images or collector numbers and its CDN is forbidden, so art comes only from the linked TCGTracking product. Linking keys on name plus product variant within sets aligned by name (`alignsSetsByName`, `productNumberKeyOf`); the `(Foil)` sibling is stamped as `tcgtrackingFinishProducts`. Promo set `999` stays unlinked.
- Japanese Pokémon (`pokemonjp`, category 85) syncs straight from TCGTracking, not through the wrapper: English names, lang `ja`, TCGplayer product ids. Its OCR (`ocrMatchesByPrintedSetAndNumber`) matches printed set code and number, never the name.
- Yu-Gi-Oh! rows are one per printing (`<passcode>_<set code>_<rarity slug>`, `card_sets` holds only that printing; cards without printings keep the artwork id), linked by set code plus `yugiohRarityKey` ("Common / Short Print" is common; "(... Reprint)" sets skipped). TCGTracking products under a code and rarity YGOPRODeck lacks (e.g. SBC2) become fallbacks borrowing the same-name card's fields. Multi-artwork printings embed and show the linked product's image (YGOPRODeck can't say which art); same-art printings tie and OCR's set line picks.
- Digimon (`digimon`, category 63), Elestrals (`elestrals`, 83) and Union Arena (`unionarena`, 81) sync straight from TCGTracking (English only, TCGplayer product ids):
  - Digimon names drop variant tags except `(X Antibody)`; `rarePrintingSql` flags tagged promo/reprint products, never `(Alternate Art)`.
  - Elestrals names drop every `(...)`/`[...]` tag but keep the subtitle (`- Champion of Zeus`); set code is the collector number prefix (Base Set First and Kickstarter both `BS1`); `rarePrintingSql` flags serialized, box topper, holo, stamped, placement and metal, never `(Stellar)`, `(Full Art)` or `(Alternative Art)`.
  - Union Arena strips only known tags (`UNION_ARENA_PRODUCT_VARIANT_TAG_PATTERN`: number, star rarity, AP, event/promo), since others are name parts (`Eren Jaeger (Attack Titan)`); set code is the printed set before the slash (`UEPR` for release events); `rarePrintingSql` flags event, promo, gold, box topper and serialized, never star parallels.
- One Piece `cards.name` is the printed name (`onePiecePrintedName` strips `(Reprint)`, `(Parallel)`, `[Winner]`, `- OP01-001`; `data` keeps them) so same-name logic links originals to `_rN` reprints and Jolly Roger/Pirate/Textured Foils (`rarePrintingSql`); sync's data refresh also updates `name`.
- One Piece printed language code ("EN" above "BANDAI MADE IN JAPAN", OP11/PRB02 on): shared `detectPrintedLanguageCode` finds it structurally (BANDAI line anchor, short ink run above; unknown over art, never a guess) inside `printingMarksPayload`, sent as the `printedLanguageCode` form field by web, mobile and Pi; OCR and server image routes detect it from their crop. Adapter `printedLanguageCodeSql` (pre-EN products a closed list, promos and fallbacks unknown) feeds the index, and `findCardMatches` swaps to the closest same-name same-art printing that agrees (`printingMarks.languageCode`); a printing-mark winner or preferred set still wins. No template region (art and white-on-color borders misread).
- Pokémon stamps (1st Edition, Staff, Prerelease, set-logo) are TCGdex variants inside one card: `PlayingCard.stamps`, priced through `tcgplayer.stampProducts` into `stampPrices`. A copy's `collection_cards.stamp` is priced by `cardPriceFor`/SQL totals on TCGplayer only, exported as its own row and SKU, sortable via `$scan.stamp`. Only 1st Edition is detected (shared `detectCardStampRgba` against `STAMP_TEMPLATES` on the oriented dewarped card, only when the card's `stamps` include it, web, mobile and Pi); others are set by hand in card detail.

#### Finishes and foil

- Finishes come from the adapter: `PlayingCard.foilTypes`, priced via `tcgplayer.finishProducts` into `finishPrices`; `cardPriceFor` takes `{ isFoil, foilType }`. Never detect the pattern from the photo: shared `scanFoilType` only narrows the session foil type when the card has one finish in that family.
- `foilOnlyFoilType` forces foil on every save, so it comes only from catalogs (adapter finish data, then `tcgplayer_skus` variants), never a missing price; missing data means not foil-only. An adapter whose source lists finishes implements `sourceListsNonFoilPrinting`.
- Look-based foil detection is only the shared sorter nudge (every game, desktop web/Electron and Pi host; not imported photos or local mobile scanning; mobile web can configure host detection). `resolveScanFoilType` gates it with `foilDetectionEnabled` and the MTG star with `foilStarDetectionEnabled` (default off); forced and foil-only finishes stay authoritative. Detected foil uses the card's finish, then `DETECTED_FOIL_TYPE_BY_GAME_KEY`, then the first finish. `executeScanFoilNudge` requires reported limits and safe calibrated travel, confirms neutral, and on the host needs calibration applied before feeding; changed calibration waits for a new session.

#### Catalog sync and storage

- Catalog images are embedded portrait (`toPortraitCardImage` turns landscape 90° clockwise; web sync's `drawPortrait` matches). Scanners search upright and 180°, so a no-detection fallback crop is portrait too (`getDefaultCardDewarpContour` on Pi and Expo; `getDefaultCardContour` stays the on-screen box).
- Every embedding write stamps `CARD_EMBEDDING_VERSION` into `cards.embedding_version`; server-mode sync re-embeds lower versions (resumable), so bump it when normalization or embedding input changes. Browser-mode sync only adds missing vectors.
- Sync plans per card through `planCardSync` and writes through `buildCatalogCardRow`; `cards.source_data_hash` (`sourceDataHashOf`: stored columns plus data minus `volatileDataKeys`) sends only changed cards, so a new stored column derived from `data` joins the hash. `hasPartialData` stubs never overwrite a stored row.
- Pruning (`sync-job/prune.ts`) runs only after a complete fetch: a source that skips cards or sets on errors calls `markSyncFetchIncomplete`, and a prune over `SYNC_PRUNE_MAX_SHARE_OF_STORED_CARDS` is refused.
- Only sync calls upstream APIs (card sync, admin re-sync, `sync-prices`); everything else reads `card-search/stored-cards.ts`, and an unsynced card is "not found". Adapters have no `search`/`searchById`. netdeck images go through `/cards/netdeck-image/...` (URLs expire).
- Nightly card sync runs on a GitHub runner (`card-catalog-sync.yml` -> `scripts/sync-card-catalogs.ts` against `DATABASE_URL`, one matrix job per game and language, stopping at `--stop-after-minutes` and resuming next run, one combined Discord report from result artifacts). The server never sees it as a sync job (no admin status, lock or index reload); only the 60 s signature check picks it up.
- `collection_cards.card` is a slim scan-time copy referencing `cards` by `(game, lang, card_id)`, not a foreign key. Write through `toSavedCardSnapshots` (drops `raw`, alternatives become references when in `cards`); every read returning cards goes through `hydrateSavedScans`/`hydrateSavedCards` (current catalog card plus `SAVED_CARD_SCAN_KEYS`). A pruned catalog card sets read-time `isMissingFromCatalog`, and card detail (web, Expo) warns and opens the correction search prefilled with the name.
- SQL over many collection rows reads generated `card_*` columns, never `cc.card ->> ...`; catalog fields come from `cards` via `cardCatalogJoinSql`, with `CATALOG_CC_ALIAS_COLUMNS` falling back to `card_*`. Sync fills them through `catalogColumnsFor`. Long lists page on the server.

#### Collection cards: import, export, move, filter

- CSV exports are built on the server (`lib/card-export.ts`, `POST .../cards/csv-export`); clients pick format and download. TCGplayer rows carry SKU ids and the condition's SKU market price (else the printing's) from `tcgplayer_skus`, filled by `sync-prices` per changed set (`lib/tcgplayer-sku-sync.ts`); exports never call TCGTracking. `GET /storage-locations/:guid/cards/export` (JSON) stays for store app versions.

- Moving cards between collections (`POST /collections/:guid/cards/move-to-collection`, intake transfer) is same-game only, clears `bin_number`, keeps storage location, intake lot and scan-time data.
- Grids and storage lists filter through `CardFilters`/`cardFilterSql` (`routes/collections/cards-query.ts`): condition, language, finish, min/max price (org-priced copy value `scannedCardPriceSql`, so it throws without pricing). Store app versions omit those keys and get zod defaults; `finish: "all"` isn't a filter (`isUnfilteredCardsQuery`). ### Prices

- `scripts/sync-prices.ts` is scheduled only: hosted daily via `price-sync.yml` on a GitHub runner (summary to `DISCORD_WEBHOOK_URL` via `postDiscordWebhook`, else the pricing channel through the bot), self-hosters via cron or Coolify. Pull guards live in the DB. TCGplayer prices and products come from TCGTracking per set (`/pricing`, `/cards`), refetched only when `pricing_modified`/`products_modified` differs from the `tcgplayer_price_sets` marker. `CARD_API_USER_AGENT` on every outgoing request, never from request paths. TCGTracking has only `low` and `market`; missing market falls back to low.
- Every shown price is one stored record, never computed (no median, average or min across products, printings or finishes). A card resolving to several TCGplayer or Cardmarket products gets no price (`onlyPriceRecord`); a table column shows only its own field. Missing prices are a dash (shared `MISSING_PRICE_TEXT`; web `MissingPrice` with sr-only text, Expo "No price" `accessibilityLabel`).
- Never read `card.price` for display or totals: use `cardPriceFor`/`formatPrice` (web `usePriceSource().priceOf`) or server `loadOrgPricing`; SQL totals take `OrgPricing`. Currencies never mix.
- TCGplayer below NM uses the condition's SKU market price (`priceByCondition`/`priceFoilByCondition`, per finish in `finishPrices`) when synced, else NM times the condition multiplier (`cardPriceFor`, `tcgplayerHeadlinePrices`); SQL totals use multipliers only.
- Grids never sort by a game's own price fields: `cardSortableFields` hides fields matching `price` and adds one `$price.usd`/`$price.eur` per currency (org source when its currency matches, else TCGplayer/Cardmarket), ordered by `joinedScannedCardPriceSql` (finish, stamp, condition, no price last). Old field sort keys from store app versions still work.
- `card_price_history` (integer cents, one row per card and UTC day) is written only by `refreshCardPrices`, in the `card_prices` upsert transaction, only for changed rows (missing day = unchanged). Clients fill gaps with shared `cardPriceHistorySeries` from `GET /cards/price-history` (window plus the last earlier row). Headline columns only.
- `collection_cards.card` keeps its saved prices (`pricesAtScan`, added on read); never refresh prices inside it.

### Soft deletes

- Hard-deleted only: `collection_cards`, unmatched scan photos, `cards`, `webhook_endpoints`, whole-org purges. Everything else sets `is_deleted`.
- Audit tables have no foreign keys: their rows are permanent.
- Every read, count, limit check and lookup filters `is_deleted = false` (including `with:` blocks and raw SQL); fix-up writes don't. Uniqueness uses partial indexes on live rows; upserts set `isDeleted: false`.
- A new soft-deletable table needs the column, filtered reads, `DELETED_ITEM_TYPES` and `routes/admin/deleted-items-sources.ts`.

### Card matching

- Swapping the embedding model is a breaking migration. Matching is in-memory; the one SQL distance query (`cardDistanceSql`) scores an explicit id list. Old `cards_embedding_hnsw_*`/`cards_back_embedding_hnsw` indexes may linger unused; a new SQL nearest-neighbour query needs its own index and `hnsw.iterative_scan`.
- `findCardMatches` uses `lib/card-match-index.ts` (brute-force cosine per game and lang, never SQL). Segments hold int8 embeddings with per-vector scale and interned text: read rows via `cardIdOfRow`/`nameOfRow`/`setCodeOfRow`/`collectorNumberOfRow`.
- Loading uses `backgroundLoadDb` (own pool `DB_BACKGROUND_LOAD_POOL_MAX`, 120 s connect timeout; intentional RLS bypass) reading binary `halfvec_send` (pgvector 0.7+, else `vector_send`; `card-match-embedding-decoder.ts`), prefetching the next page, 3 scopes at a time (Pi 1); excludes `excludedFromMatchingSql` and flags `rarePrintingSql` at load.
- Refresh: warm at startup; reload when a sync worker closes, an admin re-vectorizes or cards are dumped; every 60 s check a count/`updated_at` signature (skipped while that game syncs) only if `loadCardsTableWriteCount` changed since the segment's last check (the signature scans the whole game). Evict idle segments above `CARD_MATCH_INDEX_MAX_MB` (1024, Pi 384). `refreshStoredData` sets `updated_at` so other processes notice.
- Snapshots (`lib/card-match-snapshots.ts`, `card-match-snapshot-format.ts`): object storage `system/card-match-index/<game>.<lang>.bin`, else `$XDG_CACHE_HOME/mault/card-match-index/`. Used only when the stamp (signature, transfer format, hash of the rendered page query) matches, skipping ~70 s of reads for mtg/en. Bump `CARD_MATCH_SNAPSHOT_FORMAT_VERSION` when segment fields, quantization or interning change; `CARD_MATCH_INDEX_SNAPSHOTS=off` disables them.
- Adapter match flags (rare, promo, printed language, printed set total, excluded) are stored on `cards` (`lib/card-match-flags.ts`) with `match_flags_fingerprint` and `match_flags_source_updated_at`; stale ones (`storedFlagsAreCurrent`) are computed from `data` and queued for a background fill (one scope at a time, `CARD_MATCH_FLAGS_FILL_BATCH_SIZE`, `FOR UPDATE SKIP LOCKED`, never touching `updated_at`). Sync never writes them, so every write to `data`, `set_code` or `card_id` must set `updated_at`; adapter SQL changes need no migration.
- Regular printings beat promos and list reprints (`rarePrintingSql`, `lib/card-search/regular-printing-preference.ts`): a promo never wins on image alone (swap to the closest same-name regular printing, searching the whole index if needed); OCR ranks regular first once preferred set, printed promo marker, set line, collector number (lettered like `123p` only when read with its letter) and set total tie. A confident printing mark or explicit preferred set still wins. FaB flags every non-Standard foiling as rare (they're foil-only and would make same-art non-foil scans foil); `foilPrintingVariants` swap printings when the foil setting changes.
- Sort by game: preset with `match_game_keys` and `autoAssignField` `scanGame` (`$scan.game`); identify routes take `matchGameKeys`, run `findCardMatches` per game and keep the closest (`lib/card-search/match-games.ts`, tagged `gameKey`). A card from another game is only a sort-only scan (`isCardFromOtherGame`), never saved.
- Identify requests go through shared `requestIdentifyWithRetries`; a `ScanIdentifyRequestError` never triggers the server-vectorize fallback.

### OCR and printed marks

- `scanOcrMode` (org `ocrEnabled` plus `highAccuracyScans`): `when-unsure` reads text only after an unsure image match (`needsTextSearch`); `every-scan` always (web and mobile in parallel with the image search, Pi after it; `by-text` picks the game from the embedding when the preset matches several).
- OCR replaces the image match only when it's unsure or OCR confirms the printing (`prefersTextMatch`), never on an unconfirmed name; an unconfirmed text match more than `UNCONFIRMED_TEXT_MATCH_MAX_DISTANCE_GAP` (0.1, untuned) worse than the image leader loses. When the read lacks words several names add (Pokémon energy read as "Basic Energy"), `preferClosestNameMissingUnreadWords` picks by image distance, never the shortest name.
- One detection pass reads every name region; keep the name whose printing is confirmed or whose image is closest. An unconfirmed match beyond `OCR_MATCH_MAX_IMAGE_DISTANCE` (0.7) is no match.
- Text and printed-number matching use the in-memory index (`findCardMatchesByText`, `findCardMatchesByPrintedSetAndNumber`; `lib/card-name-trigrams.ts` must stay score-identical to pg_trgm `similarity()`), never SQL. Any SQL comparing a scan to `cards` adds `matchingExclusionFilter(scope)` (skips Scryfall `digital`, stored Pokémon TCG Pocket); Pokémon sync skips Pocket sets (`POKEMON_DIGITAL_ONLY_SERIES_IDS`).
- Server OCR: PaddleOCR on onnxruntime-node (`lib/paddle-ocr.ts`, pinned in `constants/ocr.ts`, pre-downloaded in `Dockerfile.server`), one detection pass over full-width bands (`regionBands`), regions anchor to detected lines and only unanchored ones read their fixed box. v5 recognizer needs input height 48; the small v3 detector is deliberate (v5 server is ~9x slower on a Pi).
- `ocr.regions` (boxes actually read) are saved in diagnostics; overlays draw anchored ones as saved, and fixed reads, older scans and the matched card from `OCR_REGIONS_BY_GAME_KEY` padded equally. Printing marks (`printingMarkRegionsFor`: `PRINTING_REGIONS_BY_GAME_KEY` plus the card's stamp templates) are drawn and cropped alongside in card detail, image viewer and both health pages.
- Printed language: games with a `language` region (MTG, Lorcana, Pokémon; `PRINTED_LANGUAGE_CODES_BY_GAME_KEY`, MTG uses Scryfall codes like `SP`, `JP`, `CS`) read it every scan while the collection matches every language (`readsPrintedLanguageEveryScan`); `findCardMatchesByOcr` narrows to it when synced (`ocr.scopedToPrintedLanguage`) and `prefersTextMatch` takes that over another language's image match.
- Pokémon reads the printed total (`015/198`): `printedSetTotalSql` (TCGdex `set.cardCount.official`) ranks matching totals up; a number match from a different total doesn't count.
- Riftbound promos share the regular image, so they come from the printed `P` after the number (`readPrintedPromoMarker` -> `ocr.printedPromo` vs `promoPrintingSql`), outranking the set code.
- MTG's collector-line star is the only photo foil signal: shared `detectPrintedFoilMarkerRgba` finds it structurally on the OCR-sized crop in the chosen orientation, never the 448 px embedding image (~5 px there): last line of `PRINTED_FOIL_MARKER_BANDS_BY_GAME_KEY`, lines grouped by vertical glyph overlap (never row density), the glyph before the two language letters after rejoining split letters, height ratio plus a strict star-shape check. Wider than `PRINTED_FOIL_MARKER_STAR_MAX_WIDTH_RATIO` is merged text. PaddleOCR can't read it.
- The star is stored as `diagnostics.printedFoilMarker` and every save path (web scanner and import, Expo scanner and batch, Pi) passes it to `resolveScanFoilType`, which treats it as detected foil except for printings whose source lists only non-foil (`hasNoFoilPrinting` from `sourceListsOnlyNonFoilPrinting`).
- Printing marks separate same-art printings from memory: one group per `PRINTING_REGIONS_BY_GAME_KEY` area (adapter `printingMarkGroups`: MTG only the List icon, set symbols and promo stamps proved unreliable; FaB the top-left pitch symbol; no group = no mark) in `cards.printing_mark_groups` with `printing_mark_version`. Sync adds area grids into per-group sums in `printing_mark_references` (`real[]`, in SQL, same transaction, once per version); the server rebuilds references (mean plus consistent-cell mask) per game.
- Clients sample mark areas from the camera frame via the contour (`printingMarksPayload`); decisions save them as `printingMarks.scanAreas` so tuning uses what was sent, never the 448 px image. `findCardMatches` compares same-name printings within `PRINTING_MARK_MAX_LEADER_DISTANCE_GAP` pairwise (matched filter on differing cells aligned to their midpoint; one-sided marks use a present/absent test), promoting a clear winner or blocking the regular-printing swap. Unknown is 0 evidence. Changing an area, channel or grid bumps `PRINTING_MARK_VERSION`.

### Scan identification flow

- With both orientations on, search the last winning one first (`preferredOrientation`; Expo hand scans prefer upright) and skip the other only for a close match (`isConfidentOrientationMatch`, `PREFERRED_ORIENTATION_MAX_DISTANCE`; a close runner-up never forces it). With `every-scan`, `reportImageResult` lets an unsure image result start the other orientation without waiting for text.
- With a preferred orientation and `when-unsure`, an unsure matched preferred result starts its text read while the other orientation searches; no match waits, so a flipped card never costs OCR. The Pi host picks OCR mode per candidate and never starts early.
- Early route (`runScanWorkflow` `routeEarly`, web and Pi host, not Expo whose route reply drives feeding): with `when-unsure`, an unsure image match is offered before its text read (`onImageMatchBeforeText`, only when every close match carries its card), and the adapter routes when `earlyRouteBinOf` finds all close candidates plan the same bin (no pause, auto-assign, stamps or differing pick). Never with removal, duplicate checks, foil nudge, consensus (`matchesNeeded` > 1) or a prefetched host match.
- An early-routed scan is committed: skips stop, duplicate and foil stages, falls back to the image match if text fails, takes the routed bin (`prepareMatchedScanPlan` third arg) and flags `lowConfidenceMatch` if the final card belonged elsewhere. The save waits for the final card; the Pi host saves after the confirmed route.
- Control cards: `scanner-control-code.ts` owns the versioned `mault-control:` payload (unknown keys reject, so bump the version for new fields). Never saved; routes like unmatched; a bad card pauses. Web and Pi host read them during identify (`controlStage` `during-identify`, QR decoded in a worker): identify has no effects and early routes are held until the read clears, and the control card wins. Expo reads only after a miss (`after-miss`, jsQR is slow on Hermes).
- A sorter card arriving while the previous scan still identifies (pipelined early route) is held and captured afterwards (`captureArrivedCard`).
- The settle delay is an upper bound: web captures once `createCardSettleTracker` sees a still card, copies the expected frame (`settlesOnNextStillFrame`) to a per-station canvas and identifies from it and its detection (`SettledCardCapture`, first consensus attempt only); a capture after the full delay detects again. The Pi host relies on `grabSettledCameraFrame`.
- Phone-as-camera images never ride the stream: the phone uploads to `POST /collections/:guid/phone-camera/captures/:requestId` (held 30 s, `lib/phone-camera-captures.ts`), viewers get a `capture_response` notice and the desktop `GET`s it once; store app versions' inline `imageDataUrl` is converted by the signal route. Phones sending `capturesWhenCardSettles` in `camera_ready` get `maxCardSettleWaitMs` and wait themselves (`waitUntilCardSettles`), so the desktop skips its delay.
- Multi-card photo scan (Expo `batch-scan`): `multi-card-detection.ts` runs the single-card detector over overlapping windows, keeps card-aspect quads inside a window, merges duplicates, then `identifyCard` on padded crops. Batch saves have no bin.

### Web inference and memory

- An onnxruntime-web WASM `RuntimeError` or failed worker start is permanent for the page; never retry (the detection loop would recompile every tick).
- One worker entry per ORT build over `inference-worker-runtime.ts`: `inference.worker.ts` (plain `onnxruntime-web/wasm`) and `inference-webgpu.worker.ts` (Asyncify `onnxruntime-web/webgpu`, only for WebGPU models). Never use Asyncify for WASM: iOS 26 Safari uses gigabytes compiling it and kills the tab (WebKit bug 304810).
- Multithreading needs cross-origin isolation: nginx and Vite send COOP `same-origin` + COEP `credentialless` (nginx skips `/build` for its YouTube embed), so cross-origin iframes need `credentialless` and auth or checkout can't rely on popups. Plain-HTTP Pi LAN clients stay single-threaded. Threaded workers load ORT glue from its own file (`env.wasm.wasmPaths` with `?url` `.mjs`/`.wasm`); the bundled copy hangs.
- The web detector always runs on WASM (`alwaysRunOnCpu`, ~3x faster than WebGPU) at the default optimization level; server and mobile keep `disabled` (onnxruntime-node 1.21 crashes in `GatherSliceToSplitFusion`).
- Mobile Safari reloads canvas-heavy tabs: reuse scratch canvases, free per-scan ones with `releaseCanvases`, warp on the CPU (`warpRgba`), never WebGL.
- Web scan elapsed time is read through `useScanElapsedMs`, never the `useScannedCards()` context, which stays free of per-second state.

### Scan routing, bins and saves

- Web, mobile and Pi route through shared `resolveScanBin` (`scan-routing.ts`: pick list, auto-assign, mode dispatch, full/complete pauses); mode helpers in `evaluate-bin.ts`. Corrected or hand-added cards use `resolveCorrectedScanBin` (pick list, chaos stays put, auto-assign, rules) on web and Expo.
- Saves go through `PendingScanSavesProvider`, never directly, over shared `PendingSaveQueue` (stored locally only after a retryable failure; requests abort after `SCAN_SAVE_REQUEST_TIMEOUT_MS`), wrapped by web and Expo `PendingSavesProvider`. The Pi host keeps its own file-backed queue (stores before the first attempt, bounds recovery).
- Bin capacity is checked client-side before routing; a routed card stays pending until bin counts with a later `dataUpdatedAt` land. Web starts the save with the route command (`route` starts, `persist` awaits) and feeds on the route reply without waiting for the save (saving after the reply cost ~2 s per card). The Pi host keeps confirmed route then save.
- Save transactions call `applyScanSaveTimeouts` first (`lock_timeout` 5 s, `statement_timeout` 10 s), so a locked save fails with a retryable 500; `startScanSaveTimer` logs saves over 1 s as `[scan-save] slow ...` with stage times.
- Re-sort presets (`bin_sets.is_resort_mode`) are applied by the server save (`lib/resort-scan.ts`), so clients send ordinary saves: move the least recently scanned copy of the same printing to the new bin, rewrite its `guid` to the new scan id, clear its location, keep foil, condition and first photo; insert if none. Bin rules see the scanner's foil and condition.
- Bin capacity is the smallest of physical size (bin height, card thickness), `chaosBinSize`, the bin's `maxCards` (catch-all too) and its claimed location's free slots, via `scanBinCapacity`; `PUT /bins/bins/:binNumber` keeps `maxCards` when omitted (store app versions).
- Fill lists (`bin_sets.fill_storage_location_ids`): each bin has a stored claim (`bins.claimed_storage_location_id`, distinct, reassigned only by `reclaimFillLocations` in `lib/storage-fill-claims.ts` after list, bin, emptying and capacity changes), never recomputed by bin order. Room is `capacity - max(location_position)` (slots never reused, so `formatStorageSlot` codes stay stable). Emptying stores into the claim only with `storeInClaimedLocation(s)` (store app versions unchanged). `location_position` is 1-based: never add 1.
- Cards moved to a location get slots in scan order (`scanned_at`, then id; `moveCardsToLocation`, like `moveCollectionToLocation`), never client order.
- A card is in its bin while `bin_emptied_at` is null; `markBinsEmptied` (`lib/bin-emptying.ts`) stamps cards, so presets hold no fill state. Emptying is scoped to the sent `collectionGuid` (store app versions without it empty org-wide). Inserts with a `bin_number` stamp late saves via `lateSaveBinEmptiedAtSql`. `BinConfig.lastEmptiedAt` is derived (`loadBinEmptiedTimes`); clients refetch counts when it changes.
- Never put a collection's full card list in a stream payload; unmatched scans are paged and bin fill comes from `/cards/bin-counts`.
- Scanner foil, condition and preferred sets persist per org (web `usePersistedScanSettings`, Expo kv) through `scanSettingsForGame`: kept within a game, sets and unknown foil dropped across games, and the user is told what's still set (web toast with Reset, Expo `CameraNotice`).
- Gift reveal: saved (not sort-only) scans priced at `SCAN_GIFT_REVEAL_MIN_PRICE`+ in the org currency (`scanGiftRevealOf`, `createScanGiftRevealQueue`) open as a present: web and Expo `ScanGiftRevealHost` (web auto-close pausable, Expo a `Modal` in `(app)`); the Pi host emits `SCAN_GIFT_REVEAL_EVENT` after the confirmed save. Test from the web scanner Debug menu or Expo Admin > Debug.
- Every connected sorter is a station (tab) plus one idle standby. Background stations stay laid out (never `display: none`) so they keep sorting.

### Review and unmatched scans

- Any correct, confirm or review accept sets `is_reviewed` and clears `low_confidence_match`; `is_corrected` stays separate.
- Unmatched scans become cards only through `lib/unmatched-promotion.ts` (hand identify, `POST .../unmatched/retry`). Retry runs only on user-selected scans (at most `UNMATCHED_BULK_SELECTION_MAX`), re-matches the stored embedding and always reads the stored photo's text (`pickUnmatchedRetryMatch`), batches `UNMATCHED_RETRY_REQUEST_MAX_SCANS` ids via shared `runUnmatchedRetry`, saves matches with `low_confidence_match` so they land in review, counts against the daily scan limit and skips Discord notifications.

The web Unmatched filter and Expo unmatched pill show only unmatched scans.

### Collection reads, stats and caches

- Stats that must survive deletes read `scan_stats`/`org_daily_scan_usage`. Scan images go through `resolveScanImageUrl`.
- Scan photo downloads are rendered by the server (`lib/branded-scan-image.ts`, 2.5:3.5 plus a Figtree-outline `mault.xyz` strip; no server fonts) at `.../cards/:scanId/image/download` and public `.../scan-image/download`, since presigned URLs lack CORS. Web saves the blob, Expo shares it.
- Leaderboards (`lib/leaderboard.ts`) read `leaderboard_snapshots` (per metric, period, self-hosted variant), computed at most daily (advisory lock, in-process day cache); opt-in and names are read live. Cards per hour = each org's fastest `scan_stats.device_guid` best 15 minutes times 4 (deviceless scans excluded); periods roll from the snapshot day's UTC start.
- The scan timeline pages `/cards` newest first with totals from `GET /collections/:guid/cards/scan-timeline`, bucketed in the client's IANA zone; clients key with `scanTimelineBucketKey` and must send `deviceTimeZone()`.
- Single-card changes emit throttled `collections_changed` (`emitCollectionCardsChanged`); web refreshes through throttled `invalidateCollectionCards`, skipping queries fetched after the latest write, and the grid pauses page queries under card detail or the review grid.
- Card detail side data comes from one `GET /collections/:guid/cards/:scanId/details` (`lib/collection-card-details.ts`) via `loadThroughCardDetails`: bundle on first load only, each field's own endpoint (kept for store app versions) on refetch.

Grid pages send `rawCardData=none`, so corrections load `raw` via `withRawCardDataForRules` (`GET /cards/search/:id`) before evaluating rules; store app versions still get `raw`.
- In-process server state (locks, leases, sorter links, rate limits) is per process.
- Every in-memory read cache registers with `lib/cache-registry.ts` under a dotted name (`createKeyedCache`, `createOrgReadCache`, `createCachedValue`, `createTtlCache`, `createCatalogCardCache` do it themselves; hand-rolled `Map`s call `registerMapCache`; duplicates get `#2`). Admin > Developer > Server caches (admin only, per process) clears all (`POST /admin/caches/clear`, then reloads plan settings), one cache or keys (`/admin/caches/:name/clear`) or one org (`/admin/caches/orgs/:orgId/clear`: bumps generations, deletes keys containing the id); "Reload card match index" calls `invalidateCardMatchIndex()`.
- Repeated org reads use `createOrgReadCache` (`lib/org-read-cache.ts`, TTL 15-60 s): keys carry every input; per-role filtering (costs) runs after. `minimumMsBetweenLoads` (card summaries, 15 s) makes post-invalidation reads wait and load fresh together, never serving stale. `cardStatsCtesSql` looks up prices and catalog rows once per distinct card.
- `requireOrg` bumps the org data generation after every non-GET unless `markRequestAsReadOnly` (identify, OCR, CSV exports), as do `emitToOrg`/`emitCollectionCardsChanged`; writers outside `requireOrg` (Stripe webhook, admin restores, device alerts) call `invalidateOrgReadCaches`. Global catalog caches clear with `invalidateCardMatchIndex` and its signature check.

New caches are card-dependent unless no card save can change them. Home, overview and stats caches last 120 s, 15 s load spacing on value summary and stats report.
- Heavy card stats are stored snapshots via `readStoredSnapshot` (`lib/stored-snapshots.ts`): clean served at once; dirty, over 1 h or another UTC day served while recomputing (waits up to 1.5 s, else `isRefreshing: true`, which clients poll); different org pricing never served. A refresh clears dirty marks under the scope's exclusive advisory lock before reading (triggers hold the shared lock), and only replaces an older `compute_started_at`. Tables are server-only (plain `db`, RLS on, no policies).
- `collection_card_stats` (`lib/collection-card-stats.ts`): unfiltered `/cards/summary` and the Stats collection breakdown. Statement triggers on `collection_cards` mark `collection_card_stats_dirty` when a stats column changes; a new column those stats read joins the trigger comparison. Filtered summaries compute live.
- `org_card_stats` by `variant` (`lib/org-card-stats.ts`): `/overview` value summary, `/overview/widgets` picks (`widget-picks`), every `/stats` report (one variant per range and collection). Home variants price each distinct (collection, card, finish, stamp, condition, saved prices) group once (`pricedInventoryGroupsCtesSql`), serve stale without waiting (`servesStaleWithoutWaiting`), and during a long repricing return `pendingPayload` with `isValuePending` (counts only; clients show Calculating, Expo keeps value widgets, `/overview/widgets` skips value snapshots). Pricing saves start both refreshes (`refreshOrgCardSnapshotsForPricing`).
- `org_card_stats_dirty` is marked by the `collection_cards` triggers (wider: review flags, intake lot, cost, scan time, guid) and row triggers on `collections` (name, deleted, game, lang) and `intake_lots` (status). A refresh stamps `invalidated_at` on every variant first. `orgOverviewCache`/`widgetSummaryCache` keys carry the snapshot version.
- Single statements issued while a transaction may be open (catalog hydration, `consumeDailyScan`) use `singleStatementDb` (`DB_SINGLE_STATEMENT_POOL_MAX`, default 4), never `db`. A request holds at most one pooled connection: run cached aggregates before or after its transaction, never in parallel.

### Firmware & serial

- Protocol: `firmware/PROTOCOL.md`. Firmware has no bins; the app maps bin -> (module, direction).
- Built-in Pi module detection requires `pi-0.2.0` and `board: "raspberry_pi"` (Orange Pi too); layout capacity (3/5) is not connected count, and detection counts consecutive wired sensors only up to the first gap.
- One command at a time; every blocking wait goes through `waitMs()`; pusher moves through `setServoPosition()`.
- `{"stop": true}` (firmware 2.13.2+, Pi controller) is the only command accepted mid-command: it cuts every output and latches until `neutral`. Send it through `SerialSession.sendEmergencyStop` (bypasses the busy guard and route queue; the Pi hub bypasses its queue too) and treat `{"error":"stopped"}` as a terminal stop, never a routing or feed failure.
- Web and Expo read route and feed replies through shared `classifyRouteReply`/`classifyFeedReply` and only map the kind to their own pause and toast; never re-implement the reply ladder per app.
- `handleCommand` parses its line as `const char*` and prints replies directly. New `ModuleConfig`/`FeederConfig` fields go in `MODULE_FIELDS`/`FEEDER_FIELDS` too; changing `ModuleConfig` needs an EEPROM layout migration.
- A function whose signature uses a sketch-defined struct needs a manual prototype right after the struct.
- `FeederCalibration.feedRetryCount` is app-only (firmware ignores it, kept out of `FEEDER_CALIBRATION_FIELDS`). Web, mobile and Pi feeds go through shared `feedWithRetries`, which resends `{"feeder": true}` only on a timeout (`isFeedTimeoutReply`), never on an empty hopper or another error.
- Firmware `route` runs the feeder first when module 1 reads empty, so scan routes pass `requireLoadedCard` (`readIR` before routing) or they sort an unscanned card; only calibration routes rely on the implicit feed.
- Firmware with `sensorCheckedCommands` (2.13.4+, `pi-0.3.0`) does both module 1 checks inside the command (`route` `requireLoaded`, `feeder` `requireEmptyModuleOne` through `feedOnceRequiringEmptyModuleOne`); the `readIR` round trips stay as the fallback, and retries after a checked feed are unchecked.
- A `feedNext` route feeds only after the routed card reaches its target: feeding while it was still falling (tried for 2.13.4) jammed it between modules 1 and 2, out of every sensor's view. The 300 ms card-enter wait counts from arrival, so the feed covers it.
- Route jam recovery flaps the module whose sensor sees the card; a card no sensor sees gets every module on the way flapped once (firmware `dropCardThroughToModule`, controller `drop_through_to_module`), sized to keep a 4-module jam inside the 15 s route timeout.
- A new Pi controller version goes in `PI_CONTROLLER_VERSIONS` (unknown `pi-` versions support nothing; the foil nudge reads the same list); controller-only minimums live in `PI_CONTROLLER_FEATURE_MIN_VERSIONS`.
- `feeder` succeeds at once while a card sits in module 1, so a stuck scanned card would rescan forever: web, Expo and Pi feed after a routed card through shared `feedNextCardAfterRoutedCard` (`readIR` first; module 1 still loaded pauses as card stuck, Resume feeds unchecked), and routes to module 1 never pipeline (`routeAllowsPipelinedFeed`, enforced in `requestSorterRoute`).
- The foil nudge (shared `foilNudgeCommands`) is sized from the `pusherNudgeMaxPulse`/`pusherNudgeMaxTravelPercent` limits in firmware status (`parseFoilNudgeFirmwareLimits`); without them the app never nudges. It runs through `SerialSession.runWhenIdle` so it never lands mid-route.
- ESP32-S3 boards reboot when a USB port opens, and their untagged boot banner (no `wifi`, `uptimeMs` or `seq`) can answer the first identify `getStatus`, so web identify asks again when it gets a banner.
- Sorter names reach BLE advertising through `setName` (2.14.0+): shared `syncSorterBluetoothName` runs on connect (before binding) and when the bound device's name changes (web `use-serial`, Expo `SorterProvider`).
- "Recent sorters" are per-org local Bluetooth lists (shared `rememberRecentSorter`); web connects a recent one directly only when `navigator.bluetooth.getDevices()` returns it (preloaded, so the picker fallback stays the click's first await).
- Replies match by `seq`: use `sendRequest`/`sendRawCommand`. Minimum-firmware features go in `FIRMWARE_FEATURE_MIN_VERSIONS` with a gate and a fallback.
- ESP32-S3 builds pin `FlashMode=dio` and `PartitionScheme=min_spiffs`; `esp32-flasher.ts` writes the merged bin around NVS, never whole at 0.
- Pusher directions are mirrored (`"left"` lands right); render through `BIN_SLOTS_PHYSICAL_ORDER`, never change routes to fix the display.
- Serial controls require `useSerial().isReady`; hardware-editing pages use `SessionLock`.
- `requestPort`/`requestDevice` must be the first await in the click handler: browsers only show the picker from the originating gesture.
- Wi-Fi remote (`cloud_common.ino` plus `cloud_esp32.ino`/`cloud_wifis3.ino`): the relay is in process, so board and browser must reach the same server process; Wi-Fi is configured only over USB/BLE; never flash over `cloud`; never start Wi-Fi from `setup()`. The app gates setup on `useSerial().hasWifi`, not the board type.
- Uno R4 WiFi: Wi-Fi and BLE share the co-processor, one per boot, and switching restarts the board. Its networking runs from `cloudPoll()`, with the modem timeout under the watchdog and no joins or TLS handshakes while a command runs.
- Changing `BIN_HEIGHT_PRESETS` needs a data migration. The 3D model maps raw pulses (never percentages) to degrees; rerun the model script after changing the STEP file.

### Shared client conventions (web + Expo)

- Web matches the Expo app's structure: `/app/home` (`features/home` `HomeDashboard`, strings in the `home` namespace copied from the app) is the post-login landing on desktop and mobile web. Library holds collections, storage and trade offers behind `LibraryViewTabs`; its sidebar item stays active on all three through `NavItemDef.activePaths`. Headings use Figtree everywhere (web `--font-heading`, Expo `FONT_FAMILY.heading*`); mono only for code-like text.
- Global search ranking and `catalogGamesOf` live in shared `global-search.ts`. Collections, storage locations and settings sections match on the device; owned cards come from `GET /collections/cards/search` (inventory cards, matched on `card_name`); catalog cards from `GET /cards/search?gameKey=` once per game the org has collections for, added through `POST /collections/:guid/cards/manual`.
- Catalog results load one query per game (shared `loadCatalogGameSearchPages`/`summarizeCatalogGameSearches`, pages cached individually) so a slow game never holds back the others. Global search sends `groupBy=name` to `GET /cards/search` for one row per card name (without it the endpoint is unchanged for store app versions); `GET /cards/printings?gameKey&lang&cardId` lists every printing of that name, newest first.
- Printing order: the adapter's `releasedAtSql` (ISO date; TCGTracking fallbacks use their set's `published_on`), then regular before `rarePrintingSql`, then `releaseSequenceSql` (TCGplayer product id) for undated games, then collector number; `excludedFromMatchingSql` rows are never listed.
- Card searches (collection grid, storage and public browse through `cardFilterSql`, global owned-card search, catalog search) also find non-English cards by English name through `matchesEnglishCardNameSql` (`lib/english-card-name-search.ts`: the English printing with the same game, set code and collector number via the name trigram index, only for 3+ characters).
- Its `IN (subquery)` must never share an `OR` with the indexed name/number/set matches (forces a sequential scan of all `cards`): catalog reads (`/cards/search`, `/cards/sets`, grouped search) add it as its own `UNION ALL` branch (`storedSearchBranches`) restricted to `lang = ANY` the game's non-English languages (`languagesOfGame`), since `lang <> 'en'` also scans, and only when the search can return non-English cards.
- Card searches tied to a collection (`/cards/search`, `/cards/sets` with `collectionGuid`) default to its language: the server applies shared `cardSearchLanguageOrCollectionDefault` when `lang` is missing (`lang=all` searches every language), and web and Expo pickers, correction searches and review prefetches start on `cardSearchLanguageOfCollection`, falling back to all languages only when the collection's language isn't a card language.
- Screens never render an empty form or list while loading: use a skeleton shaped like the loaded screen, never one generic block (or `SettingsPage`'s `isLoading`). Expo: `ListSkeleton` (row's leading/subtitle/trailing anatomy), `FormSkeleton`, `SectionSkeleton`, `SwitchRowSkeleton` or a feature skeleton; web: `ListSkeleton`, `FormSkeleton`, `TableSkeleton`, `DividedRowsSkeleton`, `SettingsSectionSkeleton` and `SkeletonStatus` for the one status announcement. Seed detail screens from list caches as `placeholderData` (card detail uses `cachedCollectionCardPosition`).
- Numbers use tabular figures by default (web `body` `tabular-nums`, Expo `AppText`); only big display numbers (hero values) opt back into proportional figures.
- Counts and money in tight spots (tiles, rows, badges, chips, chart labels, widgets) go through shared `formatCompactNumber`/`formatCompactPriceInCurrency` (`1.5k`, `$15.4k USD`, exact below 1000), never `notation: "compact"` (German has no short thousands). Web: `CompactCount`/`CompactPrice` (exact value in `title` and for screen readers) and `usePriceSource().formatCompact`; Expo: `useCompactCount`/`usePricing().formatCompact` with the exact value in `accessibilityLabel`; counts inside strings use the `{{count, compact}}` i18n format.
- Card art fades in over a blurred small-image placeholder (no stored blurhash): web `CardImage`, Expo `CardArt` with `cardArtSources(card.image)`, row thumbnails `CardThumbnail`; never a bare `img`/expo-image `Image`.
- Edits update caches first and roll back on failure: web card edits in `useScannedCards` (failures toast `scannedCards.editFailed`), collection rename/delete in `useCollections` `onMutate`; Expo card mutations through `patchCardsInCaches`. Web user-initiated card removal goes through `removeCardsWithUndo` (hides at once, deletes when the Undo toast closes or the page is hidden); `removeCards` stays immediate for the sorter removal queue. Marking reviewed has no undo (the server only sets `isReviewed` to true).

### Desktop (`packages/desktop`)

- Loads the hosted web app, never a bundled copy. The web app talks to it only through the feature-detected `window.maultDesktop` bridge (`DesktopBridge` in `shared`).
- Build channel `MAULT_DESKTOP_CHANNEL` (`production` from master, `development` from dev) is baked in by tsup (`lib/channel.ts`: app URL, Windows app ID, icon) and read by `electron-builder.config.js` (app ID, name, update feed `desktop-latest`/`desktop-dev`). MAULT Dev installs next to MAULT and loads dev.mault.xyz; keep the two configs' channel lists in step.
- Publishing identity is never committed: desktop app ID from `MAULT_DESKTOP_APP_ID` (GitHub var `DESKTOP_APP_ID`, `.dev` appended on dev), update feed from `GITHUB_REPOSITORY` (or `MAULT_DESKTOP_RELEASE_REPOSITORY`); mobile `MOBILE_IOS_BUNDLE_ID`/`MOBILE_ANDROID_PACKAGE` (EAS env vars) and `EAS_PROJECT_ID` have no defaults, and store submit details live in the gitignored `packages/mobile/eas.json` (CI copies `eas.example.json`).
- Thumbnail buttons: no calls until shortly after the main window is first shown, and never pass `flags: ["enabled"]`.
- The main window hides the native title bar (`titleBarOverlay`): the web `AppTopBar` is the drag region and reserves the window controls' width through `env(titlebar-area-*)` (`useDesktopTitleBar`); its buttons, links and inputs stay `no-drag`.
- Serial permissions only allow ports picked through `device-picker.ts`; the permission handler receives Chromium's snake_case object, not the picker's.
- `backgroundThrottling: false` hides occlusion from the page, so "covered or minimized" comes from `window-state.ts`/`window-coverage.ts`.
- Document scanners (Windows only): `scanner-helper/` is a .NET helper on NAPS2.Sdk (LGPL: ship its DLLs unbundled, never single-file) streaming JSON lines; WIA only, feeding through NAPS2's WIA 1.0 mode (one page per transfer), (NAPS2 TWAIN transfers the whole hopper and reports false jams on cancel). `lib/document-scan.ts` also watches one folder picked through the native dialog (the renderer never passes paths). The web app generates `scanBatchId` and feeds pages into `useScanImageImport`'s queue; bridge methods are optional because older shells lack them.
- A document scanner can be a station's camera and feeder (camera id `document-scanner:<driver>:<id>`, helper `session` mode, one page per `feed`): it registers through `useAutoFeed`'s `registerFeedSource`, which turns off pipelined `feedNext`, and every feed must see module 1 empty before and loaded after (`document-scanner-feed.ts`).
- `MAULT_FAKE_SCANNER_DIR` adds a fake scanner (`isSimulated`) in unpackaged builds (which also load the root `.env`, `development-env.ts`); it loops over its folder's images and delivers each physical card with the sorter's own feeder, so the hopper ends the run.
- Scanner pages (station feeder, flatbed, Import scans' "Scan from scanner") are mostly flat background: `drawScanPageCardRegion` finds the card on the whole page, re-draws a full-resolution region around it (`SCAN_PAGE_CARD_REGION_MARGIN_RATIO`), detects again and snaps each edge to the outermost nearby luminance edge (`snapCardContourToScanPageEdges`; the detector's 384 px squeeze is only approximate, and an edge running off the scan stops at the image border); identify uses that contour as-is (`knownCardContour`).
- Saved scanner images are never perspective-dewarped: front and back are rotated rigidly to the card's angle and cropped to the card plus `SCAN_PAGE_CARD_CROP_MARGIN_MM` (`straightCardCropOnPage`, `scanPageCardCropDataUrl`; margin past the scan filled with the page's border color), then turned upright in quarter turns, the back by the flip the other-side layout scoring found (`backQuarterTurnsFor`); the back falls back to the front's position mirrored by `otherSideMirrorAxis` when the detector misses a card back. Never crop by brightness thresholds (light borders read as background).
- Document-scanner station scans can also be copied to a folder picked through the native dialog (`document-scan-archive.ts`, stored per machine): after routing the web app sends the oriented images with collection name and bin, and the desktop writes `<folder>/<collection>/bin N/` (no bin: the collection folder), sanitizing names for Windows.
- Flatbeds are their own mode (camera id `document-scanner:flatbed:...`, listed when the helper reports `hasFlatbed`): `useFlatbedScan` drives Scan card, then 30 s to move the card into module 1, then identify, with Rescan, Cancel and Continue keeping the scan. Auto feed is forced off. The helper scans the full glass width (never a card-sized area; driver alignment differs) down to the saved placement and the web crops it (`flatbed-placement.ts`, per scanner in localStorage). Without a sorter it shows the hand-scan bin banner.

### Business tools

- `/business` routes go through `businessQuery`; permission failures return 200 with `success: false`, never 403.
- Every path that inserts `collection_cards` stamps `intake_lot_id` via `findOpenIntakeLotId`. Cards in open or cancelled lots aren't inventory (count only `intake_lot_id IS NULL OR status = 'accepted'`, `inventoryCardSql`).
- Write costs through `updateAcquisitionCosts`; sums only include the org's current currency. Fulfilling an order hard-deletes its cards and writes permanent `card_sales`.
- Price labels (Buy & sell > Labels, web only; Expo has Intake and Picks under More > Buy and sell) read `GET /business/price-labels/cards` (collection, location or intake lot, priced on the server through `cardPriceFor`, capped at `PRICE_LABEL_CARDS_MAX`) and apply markup and rounding through shared `priceLabelPrice`; custom prices live only in the print form, never saved. Avery templates and sheet layout (`components/label-sheet`, `lib/label-sheet.ts`) are shared with storage labels.
- Cards allocated to open picks are reserved: shop catalogs and trade links (`hidesCardsReservedByOpenPicks` on the browse scope) and trade offer creation skip them through `lib/order-reservations.ts` (an uncorrelated array of allocations, never a per-row jsonb scan); view links still show them.
- Pick substitutes are ranked by shared `orderSubstituteCost` and stick because `allocateOrderLines` keeps any existing, unreserved allocation. Batch picking and packing slips are web-only views over the existing order reads (`useQueries`); batch completion is one `fulfil` call per fully picked order.
- Intake, pick and reservation lists search on the server (`q`, `lib/business-list-search.ts`, LIKE wildcards escaped) because they page there; reservations match a whole request so a result never shows half a customer's cards.
- Pick progress is server state: every tick saves through `PUT /business/orders/:guid/picked` (`line.picked`, emits `orders_changed`), shared by web, mobile web and Expo. Web and mobile walk picks through shared `buildPickWalk`/`pickWalkStops`; web "Pick on phone" shows `buildOrderPickUrl` (the web pick URL plus `org`) as a QR that the Expo scan tab opens through `parseOrderPickUrl`. "Can't find" releases the copy through `PUT /orders/:guid` `releasedScanIds`.
- Sorter alerts go through `raiseDeviceAlert`. Audit-worthy mutations call `logActivity(tx, ...)` in the same transaction; a new action needs `ACTIVITY_ACTIONS`, `ACTIVITY_ACTION_KEYS` and translations.

#### Card reservations

- `card_reservations` (`lib/card-reservations.ts`) are taken only on shop catalogs with `allows_reservations` (off by default; hold length `reservation_hold_days` from shared `CARD_RESERVATION_HOLD_DAY_CHOICES`, copied onto each reservation as `hold_days`). Catalog saves from store app versions omit both settings and leave them untouched (`shopCatalogRequestSchema`).
- One queue per `collection_card_id` (the id, not the guid, so the re-sort guid rewrite keeps it): a single `ready` holder (partial unique index) and `waiting` rows behind it in join order.
- Nothing runs on a timer: every reservation read and write first settles lapsed holds (`settleCardReservations`, planned by `card-reservation-settlement.ts` over shared `settleCardReservationQueue`), promoting the next in line with a hold starting at settle time (never backdated) and closing reservations whose card is gone as `unavailable`; mutations take a per-org advisory lock.
- Guests are the anonymous `X-Guest-Key` on `/public/shop-catalog/reservations` (plain `db`) and reserve like a trade offer: a session-stored cart (tile + button, card detail toggle, header button, composer page at `?reserve=1`) sent as one request of `scanIds` (shared `CARD_RESERVATION_CARDS_PER_REQUEST_MAX`), created all or nothing with one row per card sharing a `request_guid`.
- Stages (shared `cardReservationStage`): held = to pull; being picked once `POST .../requests/:requestGuid/pick` puts it in a pick (`card_reservations.fulfilment_order_id`, allocated to that exact copy; `allocatedElsewhere` exempts reservations linked to the order being allocated); ready for pickup (`pulled_at`) when that pick completes. Fulfilling a pick never sells a card held by an active reservation, it stamps `pulled_at` on the holder (`markReservedCardsReadyForPickup`); the sale is recorded at Picked up. Cancelling a pick unlinks its reservations. Order detail lists held copies in `reservationHeldScanIds` so completion dialogs can say they stay in stock.
- Owners (`/business/reservations`, `canFulfilOrders`) see one block per request (shared `groupCardReservationsByRequest`) and release or mark picked up a whole request (`/business/reservations/requests/:requestGuid/collect|release`; pickup takes ready cards only, waiting ones stay in line) or a single card (`/business/reservations/:guid/...`). Picked up hard-deletes the copy and writes `card_sales` at the current price.
- Signed-in customers (like trade senders): create stores `guest_user_id` from an optional bearer (own-org members get 409); `/card-reservations/mine` (`requireAuth` only, plain `db` filtered by the verified user id across orgs, settling each org first) lists, claims guest-key reservations (`/mine/claim`, rate limited), cancels and clears alerts; web Library > Trades > My reservations and the Expo Trades view's `reservations` box.
- Alerts are `card_reservations.guest_alert` (held, readyForPickup, expired, released, unavailable), set by every transition that changes what the customer sees and cleared when the list is viewed or dismissed; shown in the web alert tray and Expo alerts sheet, fetched with those queries.
- Customer lists stay live through the app stream (`lib/customer-stream.ts`): org trade/reservation events and settlement schedule a per-org check comparing each watching customer's own visible state (status, hold, queue position, alert; never queue length) and send `my_*_changed` only to customers whose state changed; a client refetches once the next hold lapses (shared `msUntilCardReservationHoldsLapse`).
- Customer lists (account and catalog page) show one block per `request_guid` (shared `groupReservationsByRequestGuid`); customers cancel a card or the whole request (`/mine/requests/:requestGuid`, `/public/shop-catalog/reservations/requests/:requestGuid`).
- The catalog keeps showing held cards so others can join the line; trade links, trade offer creation and pick allocation skip them (`hidesCardsHeldByReservations`, `notHeldByCardReservationsSql`, `allocatedElsewhere`).
- Rows end in a closed status (no soft delete, purged with the org); changes emit `card_reservations_changed` and new ones post to the Discord trade channel.
- UI: web Buy & sell > Reservations (desktop and mobile web) and the Expo Buy and sell hub's Reservations tab. For members who can fulfil orders, requests with cards to pull sit in the web notification bell and Expo alerts sheet next to pending trade offers (`useReservationRequestsToPull`, reusing the active reservations list query, refreshed by `card_reservations_changed`).

### Pi scanning

- Browser, mobile and Pi identify through shared `identifyScanImage`/`identifyScanWithConsensus`; Pi `SorterLink` adapts `SerialSession`, and route checks use `requestSorterRoute`. Keep environment-specific image IO in adapters.
- Pi matched/unmatched saves persist under the Mault state directory before API submission, retry with shared policy and recover for the initiating user/org before opening hardware; internal route calls use the process-only `SERVER_SCAN_ACTOR` binding and still run membership/RLS/plan checks, never persisted bearer tokens. Sort-only accounting keeps its ordinary one-shot path.
- `PI_SORTER=1` selects the built-in GPIO/I2C controller over its private Unix socket and authenticated `/pi-sorter` bridge; USB stays on `/pi-serial` with exclusive ownership. Pi browser clients share one server-owned physical connection with remapped reply sequences. Scans reserve mutation access; competing motion/configuration commands get busy, not queued stale motion.
- Automatic browser attachment must never move servos or run the self-test; calibration lives in `/var/lib/mault/.pi-controller/`. In GPIO mode `/public/version` reports the bundled Python controller version (`core.py`), and the firmware panel says controller updates ship with Mault instead of offering board flashing.
- `PI_SORTER=1` exposes only the built-in GPIO sorter and one station; other USB/BLE/cloud connections are blocked in UI and host transports. USB-only Linux/Pi hosts (`PI_HOST=1`, `PI_SORTER=0`) discover multiple USB controllers at authenticated `/pi-serial/devices` and NUS BLE devices through explicit `/pi-serial/bluetooth/devices` scans; each physical port has its own lock, and a missing selection never falls back to another device. Host sessions snapshot controller/camera IDs for reconnects and keep their pair until stopped; one host session per org.
- Host Bluetooth uses BlueZ/Bleak through the system Python helper, bounded on-demand scans, canonical `ble:MAC` IDs and the same exclusive port claims as USB; GPIO mode rejects BLE. Keep NUS UUIDs in shared, pass them into the helper, and keep host/headless support independent of browser Web Bluetooth.
- The Linux API service sets `API_HOST=127.0.0.1`; Pi hosts also default to loopback when unset. Remote clients use nginx (`scripts/pi/nginx-mault.conf`, ports 80 and 8080) and its HTTP/WebSocket `/api` proxy. Keep the default `0.0.0.0` for non-Pi deployments unless configured.
- Remote-browser Pi behavior (serial bridge, camera relay, hiding the connect prompt) turns on only when the API reports `piHost`: true when `PI_HOST=1` (written by `scripts/pi/setup.sh`) or `/proc/device-tree/model` is a Raspberry Pi; `PI_HOST=0` forces it off.
- A remote browser on a Pi host opens the sorter through `/pi-serial` (`lib/pi-serial-bridge.ts`); the port is claimed in `lib/pi-serial-port.ts`, so the Pi scan session and a browser can't hold it at once. The node is `root:dialout` mode `660`; `install.sh` puts `mault-service` in `video`, `dialout`, `gpio`, `i2c` and `bluetooth` (whichever exist).
- The scanner camera is the USB webcam, served by `scripts/pi/camera-ctl.py` on `127.0.0.1:8765` and exposed through the authenticated API at `/api/pi-camera` (the web server must not proxy to the helper directly). The helper lists USB cameras at `/devices`, prefers stable by-id paths and routes frame/stream/focus by validated `cameraId`; each additional camera has its own process, buffer and focus file. Frames are re-encoded to JFIF before they go out.
- Camera calibration dropdowns preview without persisting station assignments; Save persists, Discard/unmount restores the saved camera. Focus previews send `persist: false`, snapshot the original focus and restore it on Discard/unmount. Keep preview readback out of the saved form baseline, and await restoration before leaving the page.
- UVC focus readback can report the saved value while the lens is elsewhere: force manual writes through an adjacent value and reapply saved manual focus after a startup settling interval before opening the helper's HTTP listener.
- Pi-owned scanning (`lib/pi-scan/session.ts`, `/scan-session`) schedules feeding in the API process; web, Expo and Pi share `runScanWorkflow`/`runScanDisposition` for control/removal/duplicate/foil ordering and route/save stages. Feature decisions go in shared `prepareMatchedScanPlan`/`prepareUnmatchedScanPlan` (routing, finish metadata, save mode, pick-list progress) and `scanCompletionPauseReason`; hardware, HTTP, state and UI effects stay in adapters so feature changes reach the host.
- Host prefetch captures the settled frame and may run the side-effect-free `matchFrame` early; the result is used only for that frame while the match inputs (`piMatchInputsKey`) are unchanged. QR commands, removal, the foil nudge and disposition never run speculatively. Full-bin/repack holds refresh and replan the same card; routed saves and completion bookkeeping still finish after stop.
- Host scans keep their collection lock across browser releases and TTLs; only host cleanup releases it. Startup applies the saved channel/module/feeder settings before confirmed neutral positioning. Host QR target changes validate through shared control rules and activate collection/preset plus context in one actor-authorized transaction; unsaved QR/removal capacity survives context refresh until bins are emptied.
- Pi removal uses the ordinary actor-authorized copy lookup/deletion routes and shared queue policy; the authoritative queue lives in the API process and survives browser reconnects, not process restarts. Sound rules share selection across runtimes; the host emits bounded live events for observing browsers, with no host audio or history replay.
- Both sync paths use the admin "cards at a time" control; the server path sets `VECTORIZE_CONCURRENCY` on the sync worker. "Start on this computer" (`vectorizeOn: "browser"`) is offered only when the API reports `piHost`: it hands cards missing front or back vectors to the open admin page; the control limits cards in flight, `BROWSER_EMBED_WORKER_MAX` caps model workers. `crypto.subtle` is missing on plain HTTP, so model hashing falls back to `fast-sha256`. Browser offloading is for bulk sync only; live identification stays on the Pi. A fatal runtime failure stops the job until page reload.
- Installs are prebuilt release bundles, never a git checkout or on-device build: `scripts/pi/build-bundle.sh` (linux-arm64, own Node, built API with node_modules, Pi web build, `scripts/pi`) runs in `pi-release.yml` (nightly on master and by hand, app version as-is). Master publishes `pi-v<version>` and repoints the `pi-latest` release (`manifest.json` with an absolute bundle URL, `install.sh`); dev replaces the `pi-dev` pre-release with `<version>-dev.<run>`. A bundle's `release.json` names the manifest it updates from, so dev installs stay on dev.
- The pi-gen SD image (`scripts/pi/image/stage-mault`) is for first installs only: built by the Sunday run and by hand, never nightly, and kept on `pi-latest` as the image to flash before updating; when that run's app version is already released it is built from the bundle `pi-latest` points at.
- Releases unpack to `/opt/mault/releases/<version>` with `/opt/mault/current` pointing at the running one; mutable state lives in `/var/lib/mault` (`.env` and `.pi-controller` symlinked into each release, so release dirs stay replaceable). `install.sh` is the only fetcher (`--fetch-only` for the updater, `--image` in the chroot), `setup.sh` does secrets, database, sorter mode and services (first boot or after install), `mault.sh` is the `sudo mault` CLI.
- Services are systemd user units of the `mault-service` system user (linger), rendered through `scripts/pi/install-services.mjs`, which escapes systemd path specifiers and command arguments; never copy the `%h/mault` templates directly.
- Root only runs root-owned code: the API faces the network as `mault-service`, so `/opt/mault` (releases, `current`) is root-owned and read-only to it; root state (setup marker, update state and log) lives in root-owned `/var/lib/mault-system` (service group may read); root never writes, chowns or executes anything under `/var/lib/mault`.
- `scripts/pi/secure-layout.sh` (root, from `install.sh`, `sudo mault update` and the root updater) installs the root units, the `mault` command as a copy at `/usr/local/sbin/mault` and the root helpers (`boot-config.py`, `os-updates.sh`, `run-update.sh`, `trusted-tree.py`) into `/usr/local/lib/mault`, renamed into place, never symlinked into a release.
- Root runs release code only after `python3 -I trusted-tree.py --release /opt/mault/current --path <helpers>` passes (root-owned, not group/other-writable chain through `current`, no symlinks under `scripts/pi`; `--path` re-checks `/usr/local/sbin/mault` and `/usr/local/lib/mault` with their parents at every root entry point). Root scripts pin `PATH` when `$EUID` is 0 and call Python with `-I`; anything reading the service's `.env`, logs or data runs through `as_service_user`.
- Releases 1.0.209 and older (service-owned `/opt/mault`) can't switch over in place: the updated `mault` command refuses them, and `install.sh` (run fresh through `curl ... | sudo bash`) deletes an untrusted `/opt/mault` and the old `/usr/local/bin/mault` symlink, never re-owning or reading them (it uses only its own manifest URL).
- `scripts/pi/update.sh` runs as root (`sudo mault update` or `mault-update.service`), dropping to `mault-service` for user units and node helpers: it fetches the manifest's bundle (SHA-256 checked) next to the running release, stops services, switches `current`, re-renders units and starts them, and switches back when the new release does not answer. It keeps the running and previous releases; migrations run through `run-api.sh` at startup. nginx serves the web app straight from `current`, so a release is never modified in place.
- Images get login, SSH and Wi-Fi from boot-partition `mault-config.txt` (`scripts/pi/boot-config.py` via `mault-boot-config.service`, every boot, root; Imager can't customise custom images); applied passwords are erased from the file and its `Status` line reports the result. The image's own `mault-admin` password is random and unknown.
- OS patching is the board's own: `os-updates.sh` (root, from `/usr/local/lib/mault`, run by `install.sh`, `sudo mault update` and `sudo mault os-updates`) enables `unattended-upgrades` for Debian security and the Raspberry Pi archive, never auto-rebooting; the root updater re-applies it after every update. `GET /pi-update` reports `rebootRequired` (`/run/reboot-required`, or a `/lib/modules` kernel installed after boot or the running one gone) with the `bootId`, and the web shows admins a dismissible `sudo reboot` banner keyed per boot (`usePiRebootAlert`, sharing the one `usePiUpdate` poller in `AppAlertsProvider`); a failed release check doesn't hide it. Node and npm fixes reach boards only through a new Pi release.
- Browser-triggered host updates require platform admin and `piHost`, and refuse active scans, GPIO motion/reservations, USB/BLE sorter connections and sync jobs; idle GPIO viewers are closed and reconnects suspended until the update finishes or fails.
- The API only drops an empty file in `/var/lib/mault-system/requests/` (the service can create, not list or read); root `mault-update.path` starts `mault-update.service` (`run-update.sh`), which installs only what the root-owned `release.json`'s manifest names and writes `update.json` to `/var/lib/mault-system`. Without the path unit (pre-switch installs) the API asks for a one-time reinstall through the release's `install.sh`.
- A browser version mismatch means refresh; host update availability offers the manifest's `version` whenever it differs from the installed `release.json` version (not the API package version), never only when higher, so a rolled-back manifest moves boards back.

### Discord bot

- Each guild maps to one org; every channel and rule target is validated against the linked guild, and mentions are limited to the requested roles.
- New trade offers post to the org-level trade channel (`discordTradeChannelId`/`discordTradeRoleId`, notify kind `trade`): no collection overrides or threads. The embed links to the owner review page and omits the guest's contact.
- Scan notification images are rendered by the server, not the bot (`lib/discord/scan-notification-image.ts`, once per scan and only when something posts): the square 448 px scan photo squished to 2.5:3.5, the reference art beside it when the image proxy hosts allow it (else the scan alone, logged with the reason), and the download's brand strip (`renderBrandedCardRow`); the bot posts `attachmentDataUrl` as-is.
- `discord_user_links` is server-only (plain `db`, filtered by the verified `userId`). Scan notifications go through `lib/scan-notification-queue.ts`.
- Discord account linking (`/me/discord` link code, then `/link-account` in Discord) lives in web Account settings (desktop and mobile web) and Expo Profile (`DiscordAccountSection`); both poll `/me/discord` only while a code is pending (Expo only while focused) and refresh the status message settings on link and unlink.
- Customer status DMs (`lib/customer-status-messages.ts`; switches on the Sent and My reservations boxes on web and Expo; `/me/status-messages`; server-only `customer_status_messages`) send only when `BOT_URL`/`BOT_API_SECRET` are set and the user linked Discord.
- Every org trade/reservation event and settlement schedules a per-org DM dispatch that claims each change once in SQL (`trade_offers.status_messaged_at`, `card_reservations.guest_alert_messaged_at` set to the alert's `guest_alert_at`), only for changes after the switch was turned on; the bot's `/direct-messages` sends it. Reservation DMs come from `guest_alert`,: seen in the app means no DM. Signed-in creates also DM a confirmation (no claim marker, sent once from the create route).
- DMs list the cards (`customer-status-message-embeds.ts`) and links to the item: shared `sentTradeOfferWebPath` and `myCardReservationRequestWebPath` (`?request=`, which web My reservations scrolls to, focuses and drops).
- `/my-reservations` and `/my-trades` reply ephemerally with the linked user's active reservations and sent trade offers: the bot calls `/bot/my-reservations`/`/bot/my-trade-offers` with the Discord user id, and the server reuses `listMyCardReservations`/`listOutgoingTradeOffers` and builds the embed (`lib/customer-list-embeds.ts`).
- Welcome DMs (`/link-account` instructions) go only to new members of `DISCORD_WELCOME_GUILD_IDS`, never customer servers; the privileged `GuildMembers` intent is requested only when that list is set.

### Deploys

- `deploy.yml` builds GHCR images; Coolify pulls `:latest` (master) or `:dev`. Stages: plan, one build job per image, release commit and tag, deploy apps, migrate, deploy server, notify. Files the plan changes before building (version bump, OpenAPI spec, dev firmware) reach later stages only through the `release-overlay` artifact, so never change build inputs in a later stage.
- Anything that changes a baked-in file (e.g. firmware) must dispatch `deploy.yml`. The web image is rebuilt only when its change filter matches (`packages/web/`, `packages/shared/`, `Dockerfile.web`, `nginx.conf`, `docker/web-env.sh`); add any new file the image copies to that filter.
- Web `VITE_*` config is runtime: read it through `runtimeEnv()`, never `import.meta.env.VITE_*` (no build args).
- The bundled firmware version is the server reading `FIRMWARE_VERSION` from `firmware/main/main.ino` (copied into the server image; dev deploys write the dev version into it; `LATEST_FIRMWARE_VERSION` is only a fallback) through `/public/version` (`useLatestFirmwareVersion`); a change triggers the same refresh prompt as a new app version.
- Better Stack: errors via the Sentry SDKs (`lib/error-reporting.ts`, web and server, loaded only when the DSN is set); uptime monitors and heartbeats are owned by name by `scripts/better-stack-uptime.mjs` (`pnpm uptime:sync`), (new public service: add a monitor; unreachable one: a heartbeat). Monitored endpoints never touch the database (Neon scale-to-zero): the API monitor is `/public/version`, never `/public/health`.
- Mobile, desktop, firmware and Pi (`pi-release.yml`) have their own release workflows. Pi and desktop run nightly on master (04:17 and 04:37 UTC, after the nightly Release) and end green without building when there is nothing to release: Pi when the app version already has its `pi-v` tag or nothing `build-bundle.sh` reads changed since the last `pi-v` tag (`packages/*/package.json` version bumps don't count); desktop when `packages/desktop` and shared's `desktop*` files are unchanged since the last `chore(release): desktop v` commit (the commit, not the tag, so a rollback isn't undone the next night). A new file the Pi bundle copies goes in `BUNDLE_SOURCES` in `pi-release.yml`.
- Release's `deploy_to_coolify` input (default on; scheduled runs always deploy) off publishes a full release for self-hosters (bump, commit, tag, images promoted to `:latest`/`:dev`) but sends nothing to Coolify, runs no migrations and posts no announcement or Discord message. The tag marks the work released, so the nightly run won't deploy it: bring hosted up with a forced deploy, never a rollback to that tag (rollbacks skip migrations).
- Every release workflow takes a `rollback_tag` input. Release redeploys that `v*` tag under its own version, reusing its `:v<version>` images and rebuilding only missing ones, with no bump, commit, tag or migrations (the database stays on the newer schema). Desktop, firmware and mobile rebuild the tag's code under the next version from the branch, (updaters and stores never take a lower version) (firmware compiles the tag in a worktree and commits only the version line and binary). Pi (master only) copies the `pi-v*` tag's `manifest.json` and `install.sh` into `pi-latest` without building.
- `mobile-release.yml` only builds, using `packages/mobile/package.json`'s version as-is (bumped by hand; EAS auto-increments build numbers); store submission is manual (`pnpm submit:ios`/`submit:android` or `eas submit --id`). Mobile `MOBILE_*` values must be set as EAS environment variables. Firmware versions are bumped by the release workflow.

## Web conventions

- Feature-first: `features/<name>/{api,components,lib}`; cross-feature code in top-level `components/`, `hooks/`, `lib/`. API calls through `lib/api/client.ts` or `features/*/api/`.
- Forms: React Hook Form + Zod resolver, never `useState` per field. Schemas for forms both apps have live in `shared` (`schemas/forms.schema.ts`); messages are `formValidationMessage(...)` keys (`validation.*`), translated by web `FieldError` and mobile `translateFormErrorMessage`, never literal English.
- Nothing auto-saves: settings edit a draft saved through the page's single `SaveBar` with `UnsavedChangesGuard`. Draft forms take server data via `values` with `resetOptions: { keepDirtyValues: true }`; Discard passes `DISCARD_RESET_OPTIONS`. Discrete actions stay immediate.
- Hotkeys only through `useHotkeys`, declared in `HOTKEYS`. Toasts only through the root `Toaster`.
- Global search is a command palette, not a page: `GlobalSearchCommand` (shadcn `ui/command` on cmdk, `shouldFilter={false}`: results are ranked by shared `rankGlobalSearchMatches` and the server), mounted once in the app layout, opened through `openGlobalSearch()` (`Ctrl`/`Cmd`+`/` anywhere, `/` when no page search field is focusable, the Home search entry). `/app/search?q=` only redirects home and opens it with the query; catalog card pages stay under `/app/search/cards/...`.
- Settings sub-pages use `SETTINGS_PATHS`, `SettingsSection` panels and a `settings:sectionIntros` entry; moving a panel means updating `CALIBRATION_TOUR_STEPS`.
- Mobile web screens use `MobilePageHeader`, the `MOBILE_*` classes and `MOBILE_NAV_SCROLL_PADDING_CLASS` on scroll areas. Keep popovers other than `Select` out of vaul drawers: every `ui/dialog` `Dialog` is a vaul drawer below `md`, so a dialog containing a combobox or popover (including through `RuleGroupEditor`) passes `drawerOnMobile={false}`. An `overflow-hidden` child of a height-capped flex column shrinks and clips instead of letting the parent scroll, so it needs `shrink-0`.
- Bulk-selectable items (card grid and table rows, storage rows, collection tiles, intake rows) spread `modifierClickSelectHandlers` so Ctrl/Cmd-click anywhere toggles selection (capture phase, before open/navigate); the checkbox stays the keyboard path, and macOS Ctrl-click arrives as `contextmenu`, so it selects instead of opening the card menu.
- Card actions belong in `useCardActions`.
- The app stream (`lib/app-stream.tsx`) is one shared EventSource: subscribe with `addEventListener`, never `onerror`/`onopen` (they replace other consumers' handlers).
- localStorage access can throw (Safari private mode, blocked storage): always guard it.
- A new tour or first-run prompt's "seen" storage key also goes in tutorials `TUTORIAL_PRESEEDED_LOCAL_STORAGE`, or it pops up in every recorded tutorial.
- Only the `common` i18n namespace loads at startup; the app layout loads `APP_SHELL_NAMESPACES`, and a route using a namespace in `ROUTE_LOADED_NAMESPACES` wraps its loader in `withNamespaces()`.
- Route components are created with `lazyRoute` (`lib/route-chunks.ts`, feeds `RouteLoadingIndicator`); links never preload route chunks on hover or focus. The service worker registers from the app layout, never `main.tsx`, so marketing and share pages don't download the precache.
- First paint on `/app/home`: `AppLoadingGate` waits only for the org (not `/collections`), prefetches overview, widgets and pending trade offers, then flips `useSecondaryRequestsEnabled()` (`lib/initial-load-context.ts`; always true off Home). Shell and scanner queries Home doesn't show (calibration, bin counts, card summary, sounds, intake lots, announcements, health, highlights, GitHub stars) and the service worker wait for it; data visible in the shell at first paint (bins, games, devices, billing) doesn't.
- `/overview` and `/overview/widgets` never poll: `collections_changed` invalidates them at most once per `ORG_OVERVIEW_REFRESH_MS`.
- Code loaded by `vite.config.ts` (`scripts/*.ts` plugins and the `src/lib/constants` files they import) imports `shared` by relative path (`../../shared/src/<module>`), never `@magic-vault/shared`: Node can't load shared's extensionless TypeScript source (`ERR_MODULE_NOT_FOUND`). Type-only package imports are fine.
- `shared`'s `sideEffects` lists only `schemas/public-api.schema.ts` (its `.meta({ id })` calls fill zod's global registry for `openapi.ts`); a new shared module with import-time effects must be added to it.
- Pi bundles set `VITE_PI_HOST=true` in `env.js` (`SERVED_FROM_PI_BUNDLE`): `/` redirects into the app (so to sign-in) and marketing and legal routes aren't registered.
- Public marketing pages render outside the app's `QueryClientProvider`: components there use their own client or read-only stand-ins (`demo-*`).

### Presets

- The UI calls a `bin_sets` row a "preset", never a "set". Presets carry only their game's `guid`, `key` and `name` (`BinSetGame`; the full game per preset made `/bins` about 300 KB): read field definitions, finishes and card thickness from the collection's game or `/games`.
- Presets have a free-text `description` (`SET_DESCRIPTION_MAX_LENGTH`, shared `presetDescriptionFormSchema`) saved with the name through `PUT /bins/:guid` (older clients sending only `name` leave it untouched); "Save as copy" keeps it. Web edits it in the Edit preset dialog and shows it above the rules (`PresetDescriptionNote`); Expo shows it on the rules screen and edits it in the `preset-description` sheet.
- Alphabet sort passes come from shared `planAlphabetPasses`: pass 0 splits the letters into one range per sorting bin, then each range pile is sorted depth-first (one letter per bin from 6 bins up, so every card is sorted twice); `alphabetPass` indexes that plan, which store app versions still read as the old one-letter-per-bin passes.
- Multi-stage presets are `preset_workflows` with ordered `preset_workflow_steps` (`position`), each referencing an ordinary preset by guid (presets stay usable alone and can appear in many steps). Running a step makes its preset the active `bin_sets` row and marks the workflow active (`activeStepGuid`); activating a preset directly (`set-active`, `add`) deactivates the game's workflows. Re-sort applies when the active preset has `is_resort_mode` or is the active step of the active workflow with `is_resort_mode` on (`activeWorkflowStepResorts`). Moving between steps marks the previous preset's bins emptied, like an alphabet pass.

### UI style

- Borders: `--border` (aliased by `--sidebar-border`) for structural lines (plain `border`/`divide-border`/`ring-border`, never `border-foreground/N` tints; stronger lines only for selection or state); the darker `--input` (at least 3:1 on card, canvas and sidebar in both themes) only for control boundaries (`border-input` on inputs, selects, checkboxes, the unchecked switch track). Translucent control fills are `bg-border/N`, never `bg-input/N`.
- Status colors only from theme tokens (`success`, `warning`, `info`, `destructive` and shades); raw palette colors are for data only. Fix tokens rather than hand-patching dark-mode text.
- `ui/table` `Table` draws its own frame (`rounded-card border bg-card`, header and rows on white); never wrap it in another card, ring or tinted well.
- In-page notes use `Callout`, full-width bars `AlertBanner`, empty lists `EmptyState`, labelled sliders `SliderField`, progress bars and meters `ui/progress` `Progress` (`decorative` when adjacent text states the value; spans share `PROGRESS_TRACK_CLASS`), round icon wells `IconBadge` (size and tone props). Loading uses skeletons; spinners only for in-progress actions. Foil badges use `FOIL_GRADIENT_CLASS`. `text-primary` already resolves to `--primary-text`: never add `dark:text-sidebar-primary`.
- Text: `text-sm` body, `text-control` (12px on desktop; desktop `text-sm` is 13px, `text-base` 14px, phones larger) for every control and dialog body, `text-xs` secondary, `text-2xs` captions, no `text-[Npx]`. Text tokens already grow below `md`: no per-component `max-md:text-*`. Inputs stay `text-base` below `md`. Secondary text is `text-foreground/70`; `text-muted-foreground` only in `components/ui` primitives and placeholders.
- Buttons: heights come from the primitives' sizes (desktop default 28px, sm 24px, lg 32px; phones larger), never `h-*`/`text-*` classes. Use the default size (`icon` for icon-only); `sm`/`xs` only inside inputs (`InputGroupButton`, combobox chips); `icon-compact` (24px) only for picture-in-picture window controls; `xl` (48px) for touch buttons with a two-line label (phone camera); `marketing` is default size at `text-sm` for the marketing text floor. Side-by-side buttons sit `gap-1.5` apart (rows, toolbars, footers, nested `ButtonGroup`s).
- Fills must read on both the gray canvas and white cards: `secondary`, `ghost` hover and segmented tracks use `bg-foreground/6` (never `bg-muted`/`bg-secondary` on the canvas), inset wells inside cards and dialogs are `rounded-lg bg-foreground/6`, `bg-muted` is only for image placeholders, `outline` keeps its border, focus rings use a transparent offset; filled hovers `bg-primary-hover`.
- Radius: `rounded-card` (`--card-radius`: 8px desktop, 20px below `md`; `--radius` is 6px desktop, 8px phones) for cards, `SettingsSection` panels and stat tiles; `rounded-xl` overlays; `rounded-lg` other containers and controls (buttons, inputs, selects, nav items); `rounded-md` menu items and xs buttons; `rounded-sm` tiny bits and status badges; `rounded-full` avatars and count dots (mobile web also badges, switches and the shutter); never plain `rounded`.
- ClickUp-style surfaces: floating ones `shadow-popover ring-1 ring-border`; cards borderless `bg-card rounded-card` on the soft gray `background` canvas (no ring or shadow; older raw `ring-1 ring-border` cards still exist); collection and sorter tiles (`COLLECTION_TILE_CLASS`) keep a `border` with ring states; selected rows and nav items use the `selected` button variant (`sidebarItemClassName` on `bg-sidebar`, where ghost hover is invisible). Colored `Badge` tones are uppercase status pills; neutral ones stay normal case.
- Mobile web mirrors the desktop shell and language at touch sizes: `bg-sidebar` with `MobileTopBar`, pages in the `MOBILE_FRAMED_PANEL_CLASS` canvas panel (resets `--mobile-nav-space`; the scan route keeps the shell with a black panel, only nav-hidden routes are full bleed), lists are `MOBILE_LIST_CLASS` white cards with inset dividers, 8px controls (no pill buttons or chips), primary-tint active chips/segments/tabs, round icon badges.
- The `bg-sidebar` shell (desktop and mobile web) carries `SHELL_GRADIENT_CLASS`, a brand gradient behind its content (`isolate` shell, `-z-10` layer) fading out by 60%: light mode stays at `primary/10` or below so `text-foreground/70` keeps 4.5:1 for every `THEME_COLORS` entry; dark mode keeps `--sidebar` black (tinting lifts it to the canvas).
- The Expo app uses native controls, not the web look: `Button`, `IconButton` and `SegmentedControl` are Material 3 Compose (`@expo/ui/jetpack-compose`) in the base file and SwiftUI (`@expo/ui/swift-ui`) in `*.ios.tsx`; `AppTabs` is `NativeTabs` on both. `SwitchRow` toggles from the whole row and its `SwitchControl` is display-only (`pointerEvents="none"`; SwiftUI `Toggle` on iOS, sized by its `Host`, because an RN `Switch` inside a SwiftUI sheet can't be reached). On Android the Compose button draws container, ripple and semantics, with label and Tabler icon on top as `pointerEvents="none"` RN views. Radii come from `theme.ts` by role: `CONTROL_RADIUS`/`BADGE_RADIUS` (capsule) for controls and badges, `RADIUS` for containers (iOS and Material 3 scales), `CARD_ART_RADIUS`/`CARD_THUMBNAIL_RADIUS` for card images.
- Expo lists: `ListGroup` renders rows as one white `SURFACE_RADIUS` card (no dividers, rows separated by spacing, `ListRow` inset `SPACING.lg`); FlatList rows join one card through `ListGroupItem`; sheets have the gray `background`, so cards work there too.
- Web and Expo share the look: Expo screens sit on the gray `background` canvas with white borderless `Surface` cards (`SURFACE_RADIUS`; stat tiles and highlights as separate cards with round `IconBadge`s), section titles above their cards. Home and Stats open straight with the value hero (no greeting, headline or quick-action row), with live scans, cards to review and pending trade offers right under it; in Expo the hero opens Stats, top cards are a compact list, and the top bar shows the org name without switching (that lives in More). Stats insights, chart geometry (`smoothLinePath`, `sparklinePaths`, `niceCeiling`, `foldChartSegments`) and hero sparkline values live in `shared`.
- Expo `PageHeader` with `onBack` renders `NativeStackHeader`: its `options` must stay referentially stable (a new object loops `setOptions`); its actions render inside `HeaderBarItemContext`, where iOS `IconButton`s drop their own glass (iOS 26 already wraps bar items in glass).
- Desktop page headers use `PageHeader`; view switches use `ViewTabs` (underline tabs at every width; Expo `TabStrip`, `inline` beside a section title); toggles inside forms and settings stay `ResponsiveSegmented` (Expo `SegmentedControl`).
- Desktop is denser than phones: pages pad `p-4 md:px-3 md:py-2`, stacks `md:gap-2`, card grids `md:gap-1.5`, cards `md:p-2.5` (stat tiles `md:p-2`); new layouts add the `md:` step instead of desktop-sized spacing.
- Icons in shadcn primitives take no `size-*` class; standalone icons use `size-3`/`3.5`/`4`/`5`.
- Motion: short `animate-in` for new content only, with `motion-reduce:animate-none`. No route transitions.

## Code style

- **YAGNI:** don't build it until you need it.
- **DRY:** extract a pattern after the second duplication, not before.
- **Fail fast:** explicit errors beat silent failures.
- **Simple first:** write the obvious solution; optimize only when needed.
- **Delete aggressively:** less code means fewer bugs.
- **Semantic naming:** verbose, self-documenting names for variables, parameters and API endpoints, optimized for comprehension by humans and LLMs, not brevity (`waitUntilScanIsSaved: true`, not `wait: true`), in the language's own casing.
- No code comments in app code (firmware sketches keep theirs); record non-obvious things here instead. No `eslint-disable`.
- Types, interfaces and constants never live in component, hook or route files: `lib/interfaces/*` and `lib/constants/*` per package, shared ones in `shared`.
- Never use em dashes anywhere (code, copy in every locale, commits, chat).
